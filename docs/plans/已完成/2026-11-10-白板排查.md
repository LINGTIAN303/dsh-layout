# 布局白板的排查（第二十七轮）

## 背景

`client.board.js`（白板 chunk，1071 行）从加进来就没被系统查过。选它的理由很直接：它是唯一一个**复制了主 bundle 逻辑**的文件——白板要用识别结果、配置写入和通用组件，但它自己又实现了一遍结构树、控件面板和排序。

复制的代价是：主 bundle 修过的坑，白板不知道。

这轮找到两个真 bug，形状完全一致。

## 真 bug 一：白板里历史收纳条目永远显示「未收纳」，且越点越多

```js
// 旧写法
const stored = (config.storage?.[zone] ?? []).some((value) => value.id === entry.id);
const list = (draft.storage[zone] ?? []).filter((value) => value.id !== entry.id);
```

`normalizeConfig` 的 `storageZone` 会把空 id **整个删掉**，所以历史条目在运行期**没有 `id` 字段**（`undefined`）。于是：

| 操作 | 结果 |
| --- | --- |
| 看开关 | `undefined === 'task-board'` 恒假 → 永远显示「未收纳」 |
| 点开 | 过滤条件 `undefined !== 'task-board'` 恒真 → 老条目删不掉，又 push 一条新的 |
| 再点开 | 配置里变成两条同名条目，主 bundle 的 StorageCard 显示成两行、开关删不干净 |

主 bundle 第二十一轮修过这个坑（8 处 `entry.id !== ''` 换成 `hasStorageId`），第二十六轮又发现 `guideZone` 漏了一处。白板这份实现**整体没跟上**。

### 一个中途踩的错

第一版我把它改成了「两边各算一个身份键再比」——对称的：

```js
const keyOf = (value) => (typeof value.id === 'string' && value.id !== '' ? value.id : `${value.kind ?? ''}\u0000${value.label}`);
const stored = (...).some((value) => keyOf(value) === keyOf(entry));
```

看着很合理，探针立刻报红。原因是**这个场景天然不对称**：配置里的老条目没有 id（算出 `\0任务看板`），界面上的条目有 id（算出 `task-board`），两个键永远不同。

正确规则是主 bundle 的 `findStoredFor` 那套**非对称**判据：**以配置条目为准**——它有 id 就比 id，没 id 才退回比 label+kind。

```js
const sameEntry = (value, entry) => {
  if (typeof value.id === 'string' && value.id !== '') return value.id === entry.id;
  return value.label === entry.label && (value.kind ?? '') === (entry.kind ?? '');
};
```

主 bundle 那边有 StorageCard 的补 id effect 兜底（把历史条目补上 id），白板没有那个 effect，所以必须直接判对。

## 真 bug 二：白板的槽位「上移 / 下移」点下去没反应

```js
// 旧写法
const order = config.slots.order?.[key] ?? item.order ?? 0;
draft.slots.order[key] = order - 1;   // 上移
```

`slots.order` 存的是**相对序号**，但条目原来的 `order` 由宿主注册优先级决定——实测是 **10 / 20 / 30** 这种值，不等于视觉序号。

于是对第二个条目点「上移」：`20 → 19`，仍大于第一个的 `10`，**位置不动**。用户看到的是「按钮点了没反应」。

主 bundle 第八轮就修过：改成「与相邻项交换后整组重写 `0..n-1`」。白板没跟上。

### 修法

```js
const moveBy = (id, delta) => {
  const at = visualIds.indexOf(id);
  const to = at + delta;
  if (at < 0 || to < 0 || to >= visualIds.length) return;
  const next = [...visualIds];
  const [moved] = next.splice(at, 1);
  next.splice(to, 0, moved);
  host.updateConfig((draft) => {
    for (const [index, entryId] of next.entries()) draft.slots.order[`${group.slot}::${entryId}`] = index;
  });
};
```

顺带补上**首尾禁用**：旧实现没有边界判断，连续点「上移」会把 order 一路减到负数（探针实测 60 次 → `-40`），视觉上早已到顶但按钮永远可点。

## 一个可复用的判据

这轮两个 bug 是同一个形状，值得单独记一笔：

> **凡是「同一份配置被两个文件各实现一遍」的地方，主 bundle 修过的坑都要问一句「白板那份改了吗」。**

白板和主 bundle 共享 `config` 这一个真相源，但各自实现了一层「读配置 → 生成控件 → 写配置」。这类双实现必然漂移，而且**漂移是静默的**——两处都能跑，只是行为不一致。

具体到这次：白板复制了 `PluginSourcesCard` 的排序逻辑、`StorageCard` 的身份判定，两处都停在主 bundle 修复之前的版本。

## 建议手测

1. 打开布局白板（面板里「打开白板」），进「控件」栏找 `store:` 开头的收纳入口：如果配置里有历史收纳项，开关应显示**已收纳**；点开关应变成 1 条而不是多出一条。
2. 在白板的「控件」栏里找 `entry:` 开头的槽位条目，点「上移」：条目应**真的换到上一位**（以前点下去视觉无变化）。首条的上移按钮应禁用。
