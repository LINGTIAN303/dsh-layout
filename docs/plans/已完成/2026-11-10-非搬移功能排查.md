搬移相关功能经过十六至二十轮密集排查后基本稳定，用户要求转向其他功能。这一轮不指定目标，按「改动最复杂、最近没碰过」挑：

| 候选 | 为什么选/不选 |
| --- | --- |
| `normalizeConfig`（266 行） | 唯一配置入口，所有导入/宿主读取/方案切换都过它 → **选** |
| `apply`（431 行） | 主体是装配，逻辑分散在各 ctx.effect 里，单读收益低 |

## 真 bug 一：无 id 条目的收纳开关完全无效，且会中断整条注解链

`normalizeConfig` 的 `storageZone` 会把空 id **整个删掉**：

```js
if (id !== '') record.id = id;   // 没有稳定 id → 条目根本没有 id 字段
```

所以运行期条目的 `id` 是 `undefined`，不是空串。而运行期代码写的是 `entry.id !== ''`——`undefined !== ''` 为真，于是走错分支：

| 位置 | 后果 |
| --- | --- |
| `findStoredFor` | 进入 id 分支后 `continue`，**label 兜底分支永远到不了** → 无 id 条目的收纳开关完全不生效 |
| 按钮匹配 | 进入 `entry.id.startsWith(...)` → **TypeError** → `annotateStored` 整个中断，后面所有入口都不生效 |
| 视图菜单 | `filter((entry) => entry.id !== '')` 放行无 id 条目 → `undefined` 当 React key |

实测复现（旧逻辑）：`findStoredFor([{label:'模型'}], anyIdentity, '模型')` 返回 `null`，而期望是命中该条目。

修法：新增 `hasStorageId(entry)`（判「非空字符串」），替换 6 处风险写法（L4436/4463/4468/4489/4490/7062/7087/7110 一带）。

这条与「身份键判空要判非空字符串」是同一类坑——那处在 `storageKeyOf` 里早就修过，但这几处漏了。

## 真 bug 二：方案表超限写回是死代码

```js
const state = readLayouts();                              // 内部已 break 到 LAYOUTS_MAX
if (state.list.length > LAYOUTS_MAX) writeLayouts(state); // 恒假
```

注释写着「写回是为了让存储与内存一致」，但读取阶段已截断，返回长度永远不超过上限，条件恒假。

影响：存储里 25 条方案时，第 21..25 条既读不出来、也永远留在存储里，不清理也不提示。

修法：让 `readLayouts()` 自己报告 `truncated`（只在真的因上限 `break` 时置位），`readLayoutsNormalized` 据此写回。三种情形都验过：真截断→写回、正好上限→不写回、只含脏条目→不写回。

## 留下的教训

`undefined !== ''` 是 JS 里最容易写出来的假判空。凡是「某个字段可能被归一化删掉」的产物，判空都必须带类型检查（`typeof x === 'string' && x !== ''`），并且这种判断应该收口成一个函数，而不是散落在各处。
