# 面板卡片的 UI 逻辑排查（第二十五轮）

## 背景

前几轮查的是数据层（归一化、持久化、同步、规则执行器）。这轮转向**卡片组件自身的渲染逻辑**——`PluginSourcesCard`（203 行）、`ExternalUnitsCard`（185 行）、`StorageCard`、`RulesCard`、`CoverageCard`。共同点是：它们都在渲染期直接从 `config` / `targets` 派生视图，同时又有自己的 `useState`，两种状态来源混在一起。

找到四处缺陷，全部先写断言复现、再改代码。

## 缺陷一：自动补 id 被记成「用户改动」，还原按钮永远点不掉

`StorageCard` 有一个 effect 把历史条目补齐 id（早期数据里 `{ label: '任务看板' }` 没有 `id`，而当前发现的同一条目有稳定 id `task-board`，不补就永远配不上、开关点了没反应）。

它调的是 `updateConfig`，而 `updateConfig` 默认会 `markDirty`：

```js
updateConfig((draft) => { /* 补 id */ });   // 旧写法：被当成用户改动
```

后果分两层：

| 层 | 表现 |
| --- | --- |
| 直接 | 一打开面板就显示「有未保存改动」，用户没动过任何东西 |
| 循环 | 点「还原」→ 配置退回补 id 前的形态 → effect 因 `config.storage` 变化再次触发 → 再次补 id、再次记脏 → **还原按钮永远亮着，点多少次都不消失** |

第二层是真正的死结：还原动作本身制造了让 effect 重新触发的条件。

### 复现（旧逻辑）

| 步骤 | `dirty` |
| --- | --- |
| 面板挂载，effect 补 id | **true**（用户没动过） |
| 点还原 | false |
| effect 再次触发 | **true**（还原失效） |

### 修法

传 `silent: true`——这不是用户改动，是历史数据的自动补全，不该进脏标记、也不该成为还原点：

```js
updateConfig((draft) => { /* 补 id */ }, { silent: true });
```

`updateConfig` 早就支持 `silent`（`const before = options.silent === true ? null : snapshot.config;`），只是这处没传。`silent` 此前**全仓无人使用**，属于「写了但没接上」的能力。

## 缺陷二：插件来源的计数与可见行口径不一致

`pluginSourcesCount` 显示的条目数按「未开显示全部时只算已渲染」：

```js
const itemCount = groups.reduce((sum, group) => sum + (showAll ? group.items.length : group.rendered), 0);
```

但组内列表用的是 `itemsOf`，未开 `showAll` 时**只做了搜索过滤，没过滤未渲染条目**：

```js
const itemsOf = (group) => (slot 命中 ? group.items : group.items.filter(matchesItem));   // 少了 rendered 过滤
```

于是标题写「条目 2 · 已渲染 2」，下面挂着 3 行——用户按计数去数永远数不上，且分不清哪一行是未渲染的。

### 复现（旧逻辑）

| 槽位 | 计数 | 实际行数 |
| --- | --- | --- |
| 2 已渲染 + 1 未渲染，未开 showAll | 2 | **3** |

### 修法

`itemsOf` 也按同一口径过滤：

```js
const itemsOf = (group) => {
  const base = group.slot.toLowerCase().includes(query) ? group.items : group.items.filter(matchesItem);
  return showAll ? base : base.filter((item) => item.rendered);
};
```

槽位名命中时整组保留的原有语义不变（仍按同一口径过滤，不是无条件全列）。

顺带删掉 `matchesGroup`——它从写下就没被调用过（死代码），留着会和新加的过滤逻辑混淆。

## 缺陷三：「添加规则」被挂载那一刻的空数据永久卡死

`RulesCard` 的下拉默认值用 `useState` 惰性初值：

```js
const [hideTarget, setHideTarget] = React.useState(sourceOptions[0]?.id ?? '');
```

`useState` 初值**只在挂载时求一次**。面板若开在识别不到任何搬移源的页面（插件页刚打开、设置浮层还没渲染），`sourceOptions` 为空 → `hideTarget` 落成 `''`；之后切到有源的页面，`sourceOptions` 有值了，但 state 仍是 `''`。

结果：`canAdd = hideTarget !== ''` 恒假，**「添加规则」按钮永久禁用**，用户只能关掉面板重开。方案列表（`schemeId`）、容器清单（`container`）、条件值（`condValue`）四处同病。

### 复现（旧逻辑）

| 时刻 | 可选项 | `canAdd` |
| --- | --- | --- |
| 挂载（页面无源） | `[]` | false |
| 切到有源页面 | `[block:sidebar]` | **false（仍然禁用）** |

### 修法

在**渲染期**校验当前值是否还在可选项里，失效就退回第一个可选项——但**不回写 state**：

```js
const pickValid = (value, options) => (options.some((option) => String(option.value) === String(value))
  ? value
  : (options[0]?.value ?? ''));
const hideTargetNow = sourceOptions.some((option) => option.id === hideTarget) ? hideTarget : (sourceOptions[0]?.id ?? '');
```

四条派生值 `condValueNow` / `hideTargetNow` / `containerNow` / `schemeIdNow` 统一喂给 select 的 `value` 与 `canAdd` / `add`。

不回写 state 是关键：渲染期写状态会引发「渲染 → setState → 再渲染」的循环。用户的选择只在用户自己 `onChange` 时进 state，派生值只在渲染时兜底。

## 缺陷四：登记 / 清空登记后行上的档位不更新

外部单元扫描有 1.5 秒缓存（`SCAN_SCROLL_MS`），而「声明 / 登记」档位是在**扫描时**按登记表算出来的：

```js
if (unit.tier !== 'declared' && registered.has(unit.key)) unit.tier = 'registered';
```

`registerPage` / `clearRegistry` 写完登记表就调 `refresh()`，但缓存还在有效期内 → 拿到同一份旧 `units`（`tier` 仍是 `auto`）→ 行上不出现「登记」标记。用户以为登记没生效，再点一次。

### 复现（旧逻辑）

| 操作 | 距上次扫描 | 行上档位 |
| --- | --- | --- |
| 点「登记」 | 0ms（缓存命中） | **auto（没变化）** |

### 修法

登记表是扫描的输入，改了输入就该失效缓存：

```js
registerExternalPage(external.pageKey, externalUnits);
externalScanCache = { pageKey: '', root: null, at: 0, units: [] };   // 失效，让 refresh 真扫一遍
refresh();
```

清空登记同理（要退回 `auto`）。

## 一个更明确的模式：两套状态来源混用

前四轮的缺陷是「假设被后续改动静默失效」，这轮的四处在形态上更具体：**同一个视图同时从「外部数据」和「组件 state」取状态，而两者可以不同步**。

| 缺陷 | 外部数据 | 组件 state | 不同步的后果 |
| --- | --- | --- | --- |
| 一 | 发现清单里的稳定 id | 配置里的历史条目 | 补全被当成用户改动 |
| 二 | `group.rendered` 计数 | `itemsOf` 的过滤结果 | 计数与行数对不上 |
| 三 | `sourceOptions` 当前值 | 挂载时的初值 | 按钮永久禁用 |
| 四 | 登记表 | 1.5 秒扫描缓存 | 档位标记不更新 |

判据：**凡是「渲染期从 props/外部数据派生」和「useState 记住」同时存在的地方，就要问一句「外部数据变了，state 会跟着变吗」**。不会变的那些，就是这类缺陷的所在。

## 建议手测

1. 打开布局面板的「入口收纳」页：**不应**直接显示「有未保存改动」；如果之前显示过，点「还原」后应该真的消失。
2. 「插件来源」页：标题的「条目 N」应该等于下面实际能数出来的行数。
3. 「区域搬移」页：在识别不到源的位置打开面板，然后切到会话页（有源），此时「添加规则」应可用，不需要关面板重开。
4. 切到任意第三方插件页，在「外部插件单元」卡片点「登记」：行上的档位应立刻变成「登记」；点「清空登记」应立刻退回无标记。
