# 配置同步与联动规则的排查（第二十四轮）

## 背景

持久化的迁移门禁修完之后，接着查它下游的两块：**配置同步（双向镜像）** 与 **联动规则的切方案执行器**。共同点是「一次操作写两份配置」或「一次规则执行替换整套配置」，都属于容易自激的结构。

## 真 bug 一：顺序同步「先全删再全写」会丢用户排序

`syncSlotsFromPanelOrder` 早先是：

```js
for (const link of links) delete draft.slots.order[link.key];                                    // 全删
for (const link of links) { const at = panelOrder.indexOf(link.label); if (at >= 0) slots.order[link.key] = at; }  // 只写找得到的
```

「找不到位置」的那些 link，order **被永久删掉**。

触发条件：插件已渲染过（link 已建立）但此刻不在场（面板被隐藏、插件临时卸载），且它的 label 从未写进 `panelOrder`。这时用户拖动任意一个**其它**面板就会清掉它。

更糟的是这类条目往往也不在排序列表里——列表只合并 `config.panelOrder` + 当前已渲染的面板——**用户看不到它，也就无从恢复**。

### 复现（旧逻辑）

| 输入 | 结果 |
| --- | --- |
| `slots.order` = {a:0, b:1, c:2}，`panelOrder` = [A, B] | 拖动后 c 的 order 消失 |

### 修法

只重写能定位到的 link，定位不到的原样保留：

```js
for (const link of links) {
  const at = draft.sidebar.panelOrder.indexOf(link.label);
  if (at >= 0) draft.slots.order[link.key] = at;   // 找不到就跳过，不删原值
}
```

顺序值多留一条无害，丢了就是用户排序丢失。

**副作用（可接受）**：残留的 order 会让 `syncPanelFromSlots` 反向同步时把这些面板排进列表——这其实是**恢复**，用户终于能看到并管理它们了。

**已知边界**：隐藏同步在 link 不在场时直接 `return`，不删数据但也不同步。这是「不在场就无法建立对应关系」的固有边界，不会丢数据，优先级低于顺序丢失。

## 真 bug 二：切方案规则会覆盖用户的后续改动

`applySchemeRule` 的循环防护原先用**配置对象引用**：

```js
if (schemeApplied.key === plan.scheme && schemeApplied.config === snapshot.config) return false;
```

纸面上成立（应用后记下新引用），实际有洞：用户应用方案之后**任何一次操作**（点开关、拖排序）都会走 `updateConfig` → 新的 `snapshot.config` → 引用不匹配 → 下一轮 `refresh` 规则再次触发 → **用户的改动被方案覆盖**。

而 `applySchemeRule` 在**每轮 refresh 都执行**，所以是「用户每改一次就被覆盖一次」的无限重复。

### 复现（旧逻辑）

| 步骤 | 结果 |
| --- | --- |
| 应用方案 A（sidebarWidth=400） | 400 |
| 用户改成 300 | 300 |
| 下一轮 refresh | **400（用户改动丢失）** |

### 修法

判据换成「方案 id + **方案表版本**」（`layoutsVersion`），与配置对象无关：

| 事件 | 版本 | 结果 |
| --- | --- | --- |
| 用户改配置 | 不变 | 不重复应用（改动保留） |
| 覆盖保存方案 / 换 active | 递增 | 允许重新应用（原有能力不丢） |
| 切到别的方案 id | — | key 不同，立即应用 |

### 一个踩到的实现细节

第一版改成「记应用前的版本」，测试立刻显示**连续 refresh 应用了 3 次**。原因：应用动作自身会调 `writeLayouts`（切 active），它让 `layoutsVersion` 递增，于是下一轮算出的 stamp 又对不上。

修法：同时记录应用前（`stamp`）与应用后（`stampAfter`）两个版本，下一轮算出的 stamp 等于任一个都算「已应用」。只记应用前会漏，只记应用后会无限重复。

`layoutsVersion` 原本只增不读（死变量），正好拿来做锚点；顺带把它从持久化段移到方案表段声明，避免 `writeLayouts` 引用它时踩 TDZ。

## 验证

新增 `.tmp/probe-scheme-overwrite.mjs`：4 个场景（连续 refresh 只应用一次 / 用户改动不被覆盖 / 连续拖动保留最后值 / 覆盖保存后仍能重新应用）。修前 2 条 FAIL，修后全过。

七套断言全绿：frame-geometry 15、host-obstacle 16、framer-state 9、storage-id 7、indeclared 7、host-migrate 4、scheme-overwrite 7。两 bundle 语法通过；中英字典 438/438 双向 0 缺失。

## 一个反复出现的模式

连续四轮（二十一至二十四轮）找到的 bug 都是同一个形状：

| 轮次 | 缺陷 | 本质 |
| --- | --- | --- |
| 二十一 | `undefined !== ''` 假判空 | 归一化删掉字段后，判空假设失效 |
| 二十二 | 三处无界遍历 | 假设「页面规模有限」失效 |
| 二十三 | 迁移门禁用「或」 | 假设「两字段同步写入」失效 |
| 二十四 | 同步先删后写 / 引用做判据 | 假设「link 一定在列表里」「引用一定代表内容」失效 |

都是**代码写下时其假设成立，后续改动让假设失效，而失效是静默的**。这类缺陷读单个函数永远发现不了，只能按「状态迁移的完整组合」去枚举——所以每轮我都先写断言复现，再改代码。
