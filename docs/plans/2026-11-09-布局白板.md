# 布局白板（全屏工作台）

## 背景
现有编辑模式只能做两件事：在真实界面上画四个虚线框、拖两根列分隔条。它的根本限制来自识别层：**只看得见此刻渲染在 DOM 里的那一层界面**。设置页、插件详情页、右栏标签、第三方插件页面都不常驻 DOM，切过去才能调，而切过去前一层就消失了（架构文档里已记为「能识别的时候看不见，看得见的时候识别不到」）。

用户提出的替代方案：用一个白板窗口表示这是 DSH 的页面，自动拉取全量页面落入「区域 / 容器 / 槽位 / 控件」四栏，配导航与交互动作进入设置页这类需要跳转的页面层；画框表示结构、自动吸附修正位置与大小；右侧属性面板（类 Figma）用已有组件决定某区域里有什么。

## 目标与验收标准

1. 打开白板：全屏工作台，左四栏 + 中画布 + 右属性面板；真实界面在描图态半透明透出，选中节点时真实元素高亮描边。
2. 四栏能列出当前全部真实节点（区域 6 / 容器 13+ / 槽位全部 / 控件含第三方插件单元），每项 id 与配置路径可对应。
3. 宿主固定区域**直接取用不画框**：点击区域/容器即选中，属性面板给出该节点的全部可调项。
4. 浮层类（底部条、设置弹窗、本插件面板）允许自由位置与尺寸。
5. 第三方插件的入口与 UI 单元全部落入「控件」栏（复用现有 `scanExternalPageCached`）。
6. 跨页：切到设置页/插件页时白板不空，显示该页结构骨架（抽象态）并可编辑。
7. 现有能力一项不删：拖分隔条、六页面板、槽位编排、区域搬移、入口收纳、联动、布局方案、全部恢复通道。
8. 白板代码是独立 chunk（`client.board.js`），按需加载；主 `client.js` 不再无界增长。

## 结论与依据

- **宿主结构是写死的**：三栏是宿主 CSS 网格，插件不能新增「侧边栏」。因此白板不画框造结构，而是**取用宿主固定区域结构 + 改它的约束**（order / width / min / hide）。唯一例外是浮层类，配置里本就有 `settings.offsetX/offsetY/width/height` 这类像素值。
- **四栏不是四张清单，是一棵四层树**：现有代码里 `BLOCKS`、`PART_UNITS`、`surfaces`、`slotSources`、`external.units`、`arrange`、`relocateDests` 七套词汇各自一套 id 与状态，收敛成「区域 → 容器 → 槽位 → 控件」后，四栏只是按层级过滤的视图。以后收纳/搬移/编排/联动全部对着同一棵树。
- **白板不是第二渲染器**：数据只有一份（`config`），白板是它的视图与编辑器；真实界面仍由 `buildDynamicCss()` 生成的覆盖样式渲染。
- **chunk 机制已实测**：DSH `client-modules` loader 支持包内异步 chunk，正则 `^client\.[A-Za-z0-9][A-Za-z0-9._-]*\.js$`，chunk 文件用 `{ id: '<owner>', chunk: '<fileName>', factory }` 注册，`require.async('./client.xxx.js')` 按需加载，URL 由 `chunkUrl()` 从包 URL 推导。本机实测：`client.probe.js` 经 `require.async` 返回 `{ok:true, value:'chunk-ok'}`，且 `GET /plugins/dsh-layout/client.probe.js?rev=<rev>` 返回 200。

## 设计

### 结构树模型

节点 id 沿用现有形式，保证与配置路径对得上：

| 层 | id 形式 | 数据来源 | 可调项 |
| --- | --- | --- | --- |
| 区域 | `region:sidebar` | `targets.regions`、`OFFICIAL_PAGES` | order / widthMode / width / minWidth / hidden |
| 容器 | `block:panels`、`unit:conv-header` | `BLOCKS`、各 `*Parts`、`readArrangeContainers` | order / direction / columns / gap / hidden |
| 槽位 | `slot:sidebar.panellist` | `slotSources.graph` | 条目 order / hidden |
| 控件 | `entry:<slot>::<id>`、`xunit:<pageKey>::<key>`、`label:<按钮名>` | `slotSources`、`external.units`、`storageZones` | hidden / relocateTo / storeTo |

四层节点的 `layer` 字段决定进哪一栏；`path` 字段指向配置位置，属性面板只认 `path`，不再为每类节点各写一套读写。

### 画布两态

| 态 | 触发条件 | 实现 |
| --- | --- | --- |
| 描图（trace） | 目标页此刻在屏幕上 | 全屏 fixed 层，透明背景；节点矩形来自真实元素 `getBoundingClientRect()`，随 `ResizeObserver` + `MutationObserver` 重算 |
| 抽象（skeleton） | 目标页不在屏幕上 | 用几何快照画骨架：归一化坐标 × 画布尺寸；节点仍可选中、可在属性面板调整 |

几何快照需新增一层数据（现有 `areaSnapshots` 只存 `{at, ids}` 无几何）：

```text
dsh-layout/board-geometry/v1 = {
  "<pageKey>": {
    at: number,
    frame: { width, height },
    nodes: [{ id, layer, x, y, w, h, label }]   // x/y/w/h 归一化到 0..1
  }
}
```

写入时机与 `recordAreaSnapshots` 同一处（每轮 refresh 观测到该页在场时）。签名校验复用 `surface-anomalies` 机制：页面结构变了导致快照对不上时，抽象态标「结构可能已变化，建议重新抓取」。

### 工作台布局

```text
┌──────────────────────────────────────────────────────────────┐
│ 顶部：方案切换 · 页面场景（会话/插件/插件详情/设置/第三方）· 抓取 · 关闭 │
├──────────┬────────────────────────────────────┬──────────────┤
│ 四栏      │ 画布                                │ 属性面板      │
│ 区域      │ 描图态：真实界面透出 + 节点框         │ 随选中节点变   │
│ 容器      │ 抽象态：骨架                        │              │
│ 槽位      │                                    │              │
│ 控件      │                                    │              │
└──────────┴────────────────────────────────────┴──────────────┘
```

- 四栏可折叠成一行标签（窄屏时自动折叠，只留画布与属性面板）。
- 画布顶部一排场景按钮：当前页 + 已观测过的其它页；点击场景 = 切到该页（复用现有 `selectPanel` / 宿主路由）+ 画布切到该页快照。
- 属性面板顶部显示选中节点的层级路径（`区域 / 容器 / 槽位 / 控件`）与来源徽标（官方 / 第三方 / 自动识别）。

### 交互

| 操作 | 行为 |
| --- | --- |
| 点四栏任一项 | 选中该节点；画布高亮；真实界面元素描边；属性面板换成该节点的可调项 |
| 点画布上的框 | 同选中；框上有层级色（区域/容器/槽位/控件四色） |
| 拖框边（描图态，区域节点） | 改宽度（侧栏 180–640、右栏 240–900），实时写配置 |
| 拖浮层框 | 自由改位置与尺寸（`settings.offsetX/offsetY/width/height`） |
| 属性面板勾选 | 显隐；排序用上下箭头或拖拽行 |
| 「收进更多」 | 控件节点写 `config.storage.<zone>` |
| 「搬移到」 | 控件节点写 `config.relocate`，目标从 15 个已知容器里选 |

不做的：自由像素画框造新结构（宿主结构写死，做不到）；在画布上直接拖放控件组装（以属性面板勾选/排序为主，拖放只作补充）。

### 实施中修正的四个坑

1. **样式被主 bundle 清掉**：白板样式最初用 `data-dsh-layout="board"`，而 `ensureStyles()` 会删掉所有不属于自己的 `style[data-dsh-layout]`，导致白板塌成一排。改用独立属性 `data-dshl-board`。
2. **框坐标错位**：框是 absolute 定位在画布容器里的，最初塞的是视口坐标，整体偏一个侧栏宽 + 顶栏高。改为统一减去画布原点。
3. **白板被设置弹层盖住**：白板留在 `shell.overlay` 里时层级受父层限制，设置页一打开就整条被压住。改为 `createPortal` 到 `document.body`（与主编辑面板同一做法）。
4. **第三方单元被分页截掉**：控件层最初全局取前 40 条，第三方单元排在槽位条目之后被整批截掉，切到第三方插件页后一个都看不到。改为按来源分桶、各桶独立分页。

### 与最初设计的偏差

- **不再画框造结构**：宿主三栏是写死的 CSS 网格，插件无法新增区域。白板改为「取用宿主固定区域结构 + 改它的约束」，存进配置的永远是 order / width / min / hide，不存像素矩形；只有浮层类（设置弹窗几何）保留像素配置。这条是用户确认后的口径调整。
- **四栏改抽屉**：全屏三栏会把真实界面挤掉一半，描图态失去意义。改成画布铺满整层、四栏与属性面板是可开合抽屉，默认收起（描图态完全不遮挡真实界面）。
- **层级开关**：44 个框叠在一起没法看，加四层独立开关，默认只开区域 + 容器。

### 第五轮（子系统深挖：编排 / 搬移 / 恢复通道）

#### 最严重：恢复按钮落在窗口栏里点不动

恢复按钮是「界面被改坏」时的最后一道安全网，但实测它会被放到 **y=11** —— 正好在 Electron 原生 `titleBarOverlay` 那 40px 里。Web 端看着正常（`elementFromPoint` 命中自身），但在 Electron 里那一带被原生层吃掉，真实点击落不到按钮上。

根因：`anchorCandidates` 围绕控件生成四个方向的候选点，只限制了「水平不出屏」与「垂直不出屏」，没有「不进窗口栏」这条约束。控件在头部工具行时，`above` 方向的候选点就会顶进窗口栏。

修法：加 `launcherTopBound()`（按页面头栏底边算下界，下限 44）与 `launcherPointAllowed()`，接进三条产出坐标的路径——anchor 候选、free 网格、以及越界兜底。修后实测按钮从 y=11 移到 y=436。

#### 搬移源混进不可渲染条目

「区域搬移」的源下拉里混进了 `shell.overlay · context-menu`、`better-dsh-session-deletetool-dialog` 等条目，其中两个的目标节点是 **`<style>` 标签**、一个 `<span>` 是 0×0。

根因：`operationTargetOf` 只判 `role="dialog/menu/..."`，没排除不可渲染标签与零尺寸节点——它们有 fiber 但没有布局盒。

修法：`UNRENDERABLE_TAG`（style/script/link/meta/template/noscript）+ `hasBox()`（≥2×2 才算有盒）两道过滤。修后源清单从 30 项降到 25 项。

选了第一套（语义最准），余量 8px 意味着**再加一个字就会溢出**。页签条已有 `overflow-x:auto` + 隐藏滚动条兜底，窄屏实测 774px 全放下。

### 第九轮（快捷键改指向面板）

用户要求：进入编辑模式的快捷键改为打开编辑面板，不再进编辑模式。

#### 改了什么

原先 `Ctrl/⌘+Alt+L` 的 `activate()` 是 `openPanel(); setEditing(true)`，一次按键做两件事。改成只调 `openPanel()`。

理由是这两者本来是**并列的两条工作路径**，不是「入口 + 深入」的关系：

| 路径 | 工作方式 |
| --- | --- |
| 编辑面板 | 在浮层里按卡片调：滑块、开关、下拉、方案 |
| 编辑模式 | 直接在界面上拖分隔条，浮动工具条切预设 |

同时触发会让界面上铺一层可拖的虚线框、同时浮层也打开，两套交互互相干扰。编辑模式现在从面板里的「编辑模式」开关进，或恢复按钮的空白模式按钮。

配套改动：

- 快捷键注册 id 从 `dsh-layout.recovery` 改为 `dsh-layout.panel`，别名从 `layout / recovery / 布局` 改为 `layout / panel / 布局`
- i18n 键 `recoveryShortcut`（「布局：打开编辑浮层（恢复入口）」）改为 `panelShortcut`（「布局：打开编辑面板」），中英同步
- `riskyHint` 里「快捷键也能打开编辑浮层」改为「…打开编辑面板」

#### 没动的

- `Ctrl/⌘+Alt+Shift+L` 仍走 `replaceConfig(null)` 直接改配置、不经过 React，是独立硬重置通道
- 恢复按钮的空白模式三枚按钮「恢复默认 / 插件页 / 编辑模式」保持原样——那是恢复通道不是快捷键，且明确写着「编辑模式」，语义没错

#### 实测

| 场景 | 结果 |
| --- | --- |
| 按快捷键 | `panel:true`、`editing:false`，不出现编辑模式工具条 |
| 连按三次（开→再按→Esc） | 三轮全部一致，`editing` 恒为 `false`，Esc 正常关闭 |
| 面板已开时再按 | `panelCount` 恒为 1，不叠加；也不清掉用户手动开的编辑模式 |
| 面板里手动开「编辑模式」 | 工具条出现；再关掉工具条消失（两条路径互不影响） |
| `Ctrl+Alt+Shift+L` | `enabled:false`，配置恢复默认，面板保持打开 |

### 第十轮（收纳开关概率性回退）

用户报：入口收纳点某个入口收进「更多」，收了随即又被放出来，第二次点才不被放出。应用方案时也有类似现象。

#### 复现与证据

先按正常路径点开关，5 轮全对。改成**压力测试**（每轮点一次、等 800ms 观察是否回弹）后稳定复现：30 次里 3 次回退。

抓 localStorage 的写入来源，回退的每一轮都长这样：

| 时刻 | 来源 | `media-desk` 在配置里 |
| --- | --- | --- |
| t+0 | `schedulePersist`（用户改动） | **true**（已收纳） |
| t+280~450 | `applyHostDocument`（宿主推回） | **false**（被放出） |

回退 100% 来自宿主快照覆盖，不是本地逻辑。

#### 根因

`hostForm.set` 是异步的，从「发出写请求」到「宿主落地」之间，宿主仍会推来它自己那份**旧快照**。

原先的拦截判据是字符串相等：`documentText !== hostLastWritten.document` 才应用。我第一版修复是加一份 `hostPending` 比对，仍然失败——实测抓到了两份文本的差异：

```
本地写入: 5438 字节  ..."WorldSea"},{"label":"自媒体工作台","id":"media-desk"}],...
宿主推回: 5401 字节  ..."WorldSea"}],"views":[],...
```

宿主推回的是**内容更旧的另一份文本**（少了刚加的条目），既不等于 `lastWritten` 也不等于 `pending`。**任何基于字符串相等/不等的判据都拦不住它**，因为旧快照本来就和当前值不同。

#### 修法

判据从「文本是否相等」换成「**有没有写入在途**」：在途期间收到的宿主快照一律不采用。

- `hostWrite` 时记 `hostPending[field] = text`
- `hostForm.set` 的 promise 落地后（`await hostForm.set(...)`）清掉该字段的 pending
- 兜底 `HOST_PENDING_TIMEOUT = 4000ms`：写失败时不能让界面永远收不到外部改动，超时后强制清空
- `consumeHostSnapshot` 里 `hostPending[field] !== null` 就整份跳过

#### 改后实测

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 单个入口连点 30 次 | 3 次回退 | **0** |
| 单个入口连点 40 次 | — | **0** |
| 4 个入口 × 10 次（跨域） | — | **0 / 40** |
| 应用方案 6 轮 | 未测出回退 | **0 次宿主覆盖** |
| 刷新后 UI 与存储一致性 | — | 一致 |
| 静置 6 秒（超时兜底窗口外） | — | 0 次异常写入 |

应用方案这条链路本来是同一类风险（`replaceConfig` + `updateConfig` 两次写入），实测 6 轮 0 次宿主覆盖，`active` 全程保持——修的是同一个共用通道，所以一并解决。

### 第十一轮（区域搬移的形状兼容性）

用户报：搬移时各单元的位置兼容性有问题，举例——会话头是短高长宽，搬到侧栏（长高短宽）会异常。

#### 实测确认

把「会话头 → 侧栏」配上后量到的数据：

| 项 | 尺寸 |
| --- | --- |
| 会话头（原始） | **1260 × 40** |
| 侧栏（目标） | **280 × 732** |
| 投影后会话头 | **279 × 40** |

投影只按目标宽度对齐（`--dshl-tw` = 279px），不改变内部布局。会话头内部是 `display:grid`，压到 279px 后逐层量：

```
HEADER 279x40 d=grid
  headerLeading 0x30  d=flex   ← 宽度归零，整块消失
  titleRow 231x30 d=flex
    headerCorner 28x28
      BUTTON 28x28                ← 只剩一个按钮
```

`headerLeading` 直接变 **0px**，标题、视图标签、操作组全部不可见。所以「异常」不是溢出报错，而是**内容被静默压没**——没有任何提示，用户只会觉得界面坏了。

#### 根因

搬移系统完全没有形状兼容性判定：任何源都能搬到任何目标，`relocateActiveList` 只检查「源在场、目标在场、目标不包含源」，投影只做「宽度对齐 + 平移」。

#### 修法：加宽度压缩比判定 + 行内警告

判据是目标可用宽度 / 源原始宽度，低于 **60%** 视为形状不适配。只提示、不阻断——投影的语义是「用户说了算」，强行拦掉会让一些真能用的情况也做不了。

实测：「会话头 → 侧栏」比例 **22%**（1260 → 280px），行上直接标出压缩比并加警告边框；反向的「品牌行 → 会话区」不告警（窄搬宽，兼容）。

#### 一个必须绕开的测量陷阱

投影会把源节点压到目标宽度。若每轮 `refresh` 都重新量源尺寸，量到的是**压缩后**的值，压缩比永远接近 100%，判定永远不触发。

所以用 `WeakMap` 缓存「第一次（未投影时）量到的尺寸」，以节点为键——节点被 React 重建后自然失效。实测重渲染（切页再切回）后警告仍在，节点身份也稳定。

这个陷阱同样影响 `projectionCreate` 里占位符高度的取值，但那里是在打 `TELEPORT_ATTR` **之前**量的，顺序正确，没动。

#### 没做的

**没有**做自动形状适配（比如上窄列时把内部横向 flex 改纵向）。那是改宿主内部布局，宿主随时会重渲染覆盖，风险远大于收益；而且不同单元的布局机制各不相同，不存在通用的改法。这一轮只解决「用户不知道为什么会坏」。

### 第十二轮（搬移链式冲突 + 入口收纳分区）

用户要求：继续查区域搬移，另外把入口收纳的单一列表切分开。

#### 搬移：链式冲突（真 bug）

两条搬移叠在一起时出问题。实测配置「品牌行 → 面板导航」+「面板导航 → 会话区」：

| 节点 | 位置 | 尺寸 |
| --- | --- | --- |
| 品牌行 | (280, 0) | 1260 × 60 |
| 面板导航 | (280, 0) | 1260 × 212 |

两者**完全重合**（`identical: true`），z-index 都是 1100，品牌行被面板导航盖住 60px、内容不可见。

根因：占位符插进目标容器**内部**，而目标容器自己也被搬走了（`position:fixed`），占位符跟着飞过去，于是两个源落到同一处。

修法：解析搬移时剔除「目标被另一个搬移源带走（或落在它内部）」的条目——这类链式搬移没有正确落点，目标是个浮动层，里面放不了东西。源留在原位，面板那一行标「目标被搬走，暂不生效」+ 原因说明。

改后实测：重叠 0，只剩面板导航一个投影，占位符 1 个；面板正确显示「目标被搬走，暂不生效 / 目标容器本身也被搬走了」。清理配置后投影与占位符全部归零、无残留。

顺带把两处重复的解析逻辑合成 `relocateResolve`，返回 `{ active, chained }`，`relocateActiveList` 降级成一行包装。

#### 搬移：其它场景实测通过

| 场景 | 结果 |
| --- | --- |
| 嵌套搬移（品牌行 → 面板导航块） | 正常，264×60 投影到位，无形状告警 |
| 槽位出口目标 | 3 个可选（`sidebar.panellist` / `sidebar.footer.action` / `conversation.hero.options`） |
| 源与目标枚举 | 23 个源、18 个目标（15 内置 + 3 槽位出口） |

#### 入口收纳：七区分隔

原来七个分区是一串连着的标题 + 列表，分区之间没有分隔、看不出边界，而且每区各带一个独立滚动框（`max-height:200px`），嵌套感很重。

| 区 | 行数 | 各区内滚动 |
| --- | --- | --- |
| 侧栏入口 | 11 | 200 / 328 |
| 会话视图标签 | 2 | 58 / 58 |
| 右栏开始页卡片 | 5 | 148 / 148 |
| 设置页导航 | 22 | 200 / 658 |
| 插件页第三方插件 | 40 | 200 / 1198 |
| 会话头工具按钮 | 6 | 178 / 178 |
| 设置页页头操作 | 0 | — |

改成可折叠分区：

- 每区一块，块间一条分隔线；标题行同时是折叠按钮（箭头 + 名称 + 计数）
- 计数显示「已收纳/总数」，一眼看出这区还有多少能收
- **去掉区内独立滚动框**，改由面板正文统一滚（嵌套滚动是上一轮就记过的体验问题）
- 默认只展开「还有未收纳项」的区——全绿的分区展开也没有可做的事

代价与收益：卡高从 1297 → 1356（+59px，7 个标题行），但七区边界清楚、且默认只开 3 个区。全展开 1356 / 全收起 300 / 单开 632，交互实测正常。

### 第十三轮（投影落在原生窗口栏，桌面端点不动）

用户提示「Web 端不会有大问题，桌面端不一定」——直接命中了搬移的一个死角。

#### 实测确认

Electron 主窗 `BrowserWindow` 的 `titleBarOverlay.height = 40`（`.tmp/electron-main.js:20113`），原生层盖在 Web 层之上，**y ∈ [0, 40] 这一带 DOM 收得到 `elementFromPoint` 却收不到真实点击**。

而侧栏与会话区的顶边都是 **y=0**，所以任何「放在开头」的搬移，占位符必然从 y=0 开始。实测把会话头搬到侧栏：

| 项 | 值 |
| --- | --- |
| 投影节点 | **(0, 0) 279×40** |
| 被窗口栏盖住 | **40px（全部高度）** |

也就是拖拽手柄、按钮在桌面端**全部点不动**，Web 端看着完全正常。

这是同一类坑的第二次：恢复按钮早先也踩过（落点 y=11，Electron 里点不动），当时加了 `launcherTopBound` / `launcherPointAllowed`。但搬移的投影没有用这套防护。

#### 修法

`projectionStep` 里把目标位置夹到安全区下沿：

```js
const desiredTop = Math.max(target.top, projectionTopBound());
const dy = desiredTop - box.top;
```

占位符仍留在原位（目标容器布局不受影响），只让源节点下移。

**没有复用 `launcherTopBound`**：那个函数取「页头底边 + 6」，是给恢复按钮用的（按钮不该压在页头内容上）。但搬移的源节点本来就来自页顶区域，用这个保守下界会把它推到侧栏顶部内容上，反而制造新遮挡。所以另写 `projectionTopBound()` 只避开原生层本身（44 = 40 + 4 余量）。

#### 改后实测

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 会话头 → 侧栏（放在开头） | (0,0)，被盖 40px | **(0,44)，被盖 0px** |
| 品牌行 → 面板导航（不碰窗口栏） | 对齐 | 仍然完全对齐（y=54，无夹取） |
| 位移稳定性 | — | `--dshl-ty` 静置 2 秒无漂移 |

不碰窗口栏的搬移完全不受影响，夹取只在需要时生效。

#### 沉淀的诊断脚本

新增 `.tmp/probe-windowbar.js`：注入后调 `__dshlProbeWindowBar(40)`，列出所有 `[data-dshl-teleport]` 与 `[data-dshl-button]` 的坐标，标出哪些落在窗口栏里，并比对节点与占位符的纵向偏差。这类「Web 正常、Electron 失效」的问题以后先用它扫一遍。

### 第十四轮（搬移机制重构：槽位化）

#### 为什么不再逐个修补

前四轮给搬移补了形状兼容、链式剔除、窗口栏避让、帧对齐，全部有效——但用户实测后判断「这样的情况太多了」。这是对的：机制本身是「任意 22 个源 × 18 个目标 = **396 种组合**」，逐个补是补不完的。

问题不在实现，在**抽象层级**：它把搬移建模成自由拖放，而界面里绝大多数「源 → 目标」在语义上根本不成立。

#### 业界依据

查了几个成熟项目，结论高度一致——**约束优先**：

**Berth**（Electron 版 IntelliJ 布局引擎）README 直接写：

> Free-form docking allows arbitrary container nesting — and with it gets an **unbounded state space and uncountable edge cases**: the chronic ailments of the genre. Berth takes the opposite stance — the constrained IntelliJ IDEA model: tool windows exist only in **six slots**. **Enumerable by construction.**

同一份文档还有一条：

> **Commands, not gestures.** Every completed drag reduces to a core command that is also reachable from menus and code.

**JollyPixel**（web components 停靠布局）的做法是把接受策略写成属性：`drop="tabs"` / `drop="none"` / `locked`，即「**Limit what a dock accepts**」。

**MDN 容器查询**那条则说明了根因：组件不自知上下文就无法自适应——「the component itself has no awareness of its context」。

#### 改法：槽位 + 形状契约

**两层数据**：

1. `RELOCATE_SOURCE_SHAPES` —— 21 个单元各声明一个形状类别
2. `RELOCATE_SLOTS` —— 16 个槽位各声明接受哪些形状

形状类别按实测尺寸归纳（侧栏 280 宽、会话区 1260 宽）：

| 类别 | 判据 | 例子 |
| --- | --- | --- |
| `icon` | ≤32 见方 | 收起按钮 28×28 |
| `narrow` | 窄且单行 | 品牌标识 220×24、新建会话 256×38 |
| `narrow-stack` | 窄且可高 | 工作区 276×352、面板导航 264×150 |
| `wide-short` | 宽且矮 | 会话头 1260×40、标题行 1212×30 |
| `wide-tall` | 宽且高 | 输入区 1253×238 |
| `medium` | 中等宽 | 右栏内容区 |

**关键效果**：不合适的组合在**配置阶段就不出现**，而不是搬完再警告。

实测各源的可选目标数：

| 源 | 形状 | 可选目标 | 有侧栏吗 |
| --- | --- | --- | --- |
| 会话头 | wide-short | 6 | **没有** |
| 品牌行 | narrow | 9 | 有 |
| 收起按钮 | icon | 6 | 只有行内槽位 |
| 输入区 | wide-tall | 7 | **没有** |

源下拉也从 22 收到 **13**（只有声明过形状的才列出来；9 个槽位条目因为身份是运行期发现的、形状不可预知，不再作为搬移源——它们本来也没有明确的搬移语义）。

**槽位出口也要过滤**：`slotdest:*` 的宽度只有运行时才知道，用与内置槽位同一条宽度压缩比判据（< 60% 不列出）。实测会话头（1260 宽）的目标里，`sidebar.panellist` / `sidebar.footer.action` 被正确剔除，只剩宽的那个 `conversation.hero.options`。

#### 保留了前四轮的全部兜底

槽位化是**前置约束**，不是替代品。形状压缩比警告、链式剔除、窗口栏避让、帧对齐全部保留——它们现在只在「槽位声明漏了某个真实约束」时兜底，而不是主力。

#### 与 396 的对比

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 源数量 | 22 | 13 |
| 单个源的平均合法目标 | 18 | 约 6 |
| 实际组合 | 396 | 约 80 |
| 非法组合 | 只能搬完才发现 | 配置阶段不可选 |

## 风险
- **几何快照会漂移**：已做结构签名比对 + 骨架态提示 + 一键重抓（见第二轮）。仍有一处局限：只在切进骨架态时校验一次，停留期间结构再变不会实时刷新提示。
- **chunk 与主 bundle 的模块边界**：`client.board.js` 通过 `require('dsh-layout').boardHost` 取回主 bundle 的宿主面。若主 bundle 未导出该字段（旧版本），白板会抛错并被 `Boundary` 兜住，主编辑面板不受影响。
- **快照体积**：每页 64–78 节点，上限 8 页，实测 `localStorage` 约 30KB；超限按观测时间淘汰最旧页。
- **宿主修订号依赖 mtime**：chunk 的 `rev` 由包目录 mtime/ctime/size 推导，改完文件必须 touch 一次才会换 rev，否则浏览器拿到旧 chunk（实测踩过）。
- **窗口栏高度是实测值**：`titleBarOverlay.height = 40` 取自本机 DSH 主进程配置；浮层条用「页面头栏底边 + 6」计算而非写死 40，所以宿主改高度时仍能自适应，但如果哪天头栏被移除，会退回 44 的下限。
- **下钻靠几何包含**：完全重叠的兄弟节点（同一位置的两个浮层）会被判成互不包含，可能漏列；这是几何判定的固有局限，四栏清单仍可兜底。第三轮已修正「同尺寸别名把子节点全包住」与「容器被判成子级」两类误判（改用整框包含 + 面积降序 + 排除祖先）。
- **窗口化不处理变高行**：行高固定 26px，若将来某类节点要显示两行文字，需要改成测量行高。
- **顶部条与抽屉的定位互相依赖**：抽屉的 top/bottom 由顶部条与底部条的实测高度算出（CSS 变量）。**不要把这些测量结果写进 React state** —— 上一轮这么干过，窄屏换行时形成「测量 → 重渲染 → 再测量」的正反馈，直接打爆成 React #185，白板整块崩掉。写 CSS 变量只影响样式、不触发 React 更新，是这里唯一安全的做法。
- **骨架态的画布尺寸必须当场量**：它不能复用描图态的 `canvasBox` —— 那个量只在描图态更新，骨架态会拿到 `0×0` 把整张骨架乘没（实测一个框都不显示）。
- **收纳条目的身份判空要判「非空字符串」**：运行时发现的入口条目常常没有 `id` 字段（`undefined`），`undefined !== ''` 为真会返回 `undefined`，让这类条目互相全等、在界面上整批误显示为「已收纳」。
- **恢复按钮的落点必须避开窗口栏**：Electron 原生 `titleBarOverlay` 盖在 Web 层之上（本机 40px），`elementFromPoint` 在那一带仍会命中元素、但真实点击到不了。落点算法的三条坐标产出口（anchor 候选 / free 网格 / 越界兜底）都要过 `launcherPointAllowed`，否则恢复按钮可能落在 y=11 这种「Web 端看着正常、Electron 里点不动」的位置。
- **槽位条目的可操作性判定要排除不可渲染节点**：`<style>`/`<script>` 也有 fiber 但没有布局盒，不排除会混进搬移源与排序清单。
- **中英文字典必须成对维护**：`zh` 漏键时界面会静默回退显示英文（实测「切方案」动作显示成 `Switch layout scheme`）。改字典后跑一次 `.tmp/probe-i18n-keys.py` 对比两侧键集合，要求双向 0 缺失。
- **方案表读取的写回条件**：只能因为「按上限截断」而写回，不能因为「存储比内存长」写回——后者会因规范化丢弃非法条目而误判，把方案表覆盖成残缺版本。
- **宿主 profile 的 `cordis.patch.yml` 优先级高于 localStorage**：宿主要存着旧配置/旧方案，往 localStorage 注入测试数据会被读取阶段覆盖，实测时容易误判成代码 bug。改这份文件前必须备份。
- **编辑面板的五段高度是互相挤占的**：`panelHead 39 + panelTool 75 + panelTabs 38 + panelFoot 45 = 197px` 是固定开销，正文拿剩下的。往底栏或工具区加内容会直接压缩正文，加之前先量一次正文可视高度。
- **面板外壳必须比卡片暗**：外壳用 `bg-layer-2`、卡片用 `bg-layer-1`。若哪天把外壳改回 `bg-overlay`（`#61666b` 中灰），层次会整个倒过来——这个 token 在宿主里是给弹出层底色用的，不是浮层容器。
- **页签宽度只剩 8px 余量**：7 个页签实测 448 / 可用 456。改任何一个页签名前先量一次总宽，超了会横向滚动（已有 `overflow-x:auto` 兜底，但用户会看不到最后一个页签）。
- **快捷键与编辑模式是两条并列路径**：`Ctrl/⌘+Alt+L` 只开面板，不要再加 `setEditing(true)`。两者同时触发会让「浮层里调」和「界面上拖」两套交互叠在一起。
- **宿主快照的拦截判据不能用字符串相等**：宿主写是异步的，落地前推来的旧快照**本来就和当前值不同**（实测 5401 vs 5438 字节，少的正是刚加的条目）。只比字符串必然漏拦，必须用「有没有写入在途」来判定，并留超时兜底。
- **搬移只改位置、不改布局**：投影做的是「宽度对齐 + 平移」，源节点内部布局原样保留。横向铺开的单元（会话头 1260×40）搬进窄列（侧栏 280）时，宽度只剩 22%，内部 grid/flex 会把内容压成 0px 且**不报任何错**。已加宽度压缩比警告（< 60% 提示），但没有自动适配——改宿主内部布局会被重渲染覆盖，且各单元布局机制不同，没有通用改法。
- **形状判定必须缓存原始尺寸**：投影会把源压到目标宽度，之后每轮 `refresh` 再量就拿到压缩后的值，压缩比永远接近 100%、判定永不触发。用 WeakMap 以节点为键缓存首次测量结果。
- **搬移不能链式叠加**：A 搬进 B、B 又搬去别处时，A 的占位符插在 B 内部会跟着 B 一起飞，两个源落在同一处完全重合（实测品牌行 1260×60 与面板导航 1260×212 在 (280,0) 重合，前者被盖住）。已在解析阶段剔除这类条目并在面板标出原因，但**没有**做「自动改投到 B 的新位置」——B 本身是个浮动投影，里面放不了东西。
- **一切 fixed 定位的东西都要避开原生窗口栏**（本机 40px，见 `.tmp/electron-main.js` 的 `titleBarOverlay.height`）：那一带的 DOM `elementFromPoint` 命中但真实点击到不了。恢复按钮与搬移投影都已加下界，**以后再加 fixed 层必须同样处理**，否则 Web 端测不出来、桌面端点不动。用 `.tmp/probe-windowbar.js` 扫。
- **两处安全区下界不能混用**：`launcherTopBound()`（页头底边 + 6）是给恢复按钮的，要求不压页头内容；`projectionTopBound()`（44）是给搬移投影的，只避开原生层——搬移的源本来就来自页顶，用前者会把它推到别的内容上。
- **搬移的合法性由槽位表决定，不是由运行时测量决定**：`RELOCATE_SOURCE_SHAPES` 声明 21 个单元的形状类别，`RELOCATE_SLOTS` 声明 16 个槽位接受哪些形状，配置时只列兼容项。新增单元/槽位时必须同步这两张表，否则该单元不会出现在搬移源里（不会被误放，只是用不了）。运行时测量（压缩比、链式、窗口栏）是兜底，不是主力判据。
