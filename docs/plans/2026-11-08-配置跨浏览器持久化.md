# 配置跨浏览器持久化

## 目标

布局配置与布局方案原来只存在浏览器 `localStorage`。换浏览器、换 Web 端、清缓存就全部丢失——用户辛苦调好的界面直接归零。改为存进**宿主设置文档**（`~/.dsh/settings.yaml` 的 `layout` 节），跟着 DSH 安装走；`localStorage` 降级为渲染缓存。

## 结论与依据

宿主有三条持久化通道，只有一条能带上配置：

| 通道 | 可用性 | 结论 |
| --- | --- | --- |
| `localStorage` | 一直在用 | 换浏览器即丢，正是要解决的问题 |
| `ctx.get('fs')`（Host 文件系统） | 仅 Host 侧、且需宿主授权根目录 | 客户端插件拿不到，且要自己管路径与并发写 |
| `ctx.configForms`（宿主设置文档表单） | UI 插件通用通道 | **采用**：宿主负责落盘与并发，客户端只读写字段 |

`configForms` 的机制（读宿主源码确认）：

- Host 侧插件导出 schemastery `Config` 并在 `apply` 里 `ctx.settings.configure({ auto: false }, ctx.fiber)`，就把自己的配置节纳入设置文档；行 id 即命名空间，本插件是 `layout`（`cordis.patch.yml` 里已声明）。
- Client 侧 `ctx.configForms.get('layout')` 拿到 `ConfigFormController`：`getSnapshot()` 读（`{ status, value, writable, revision }`）、`subscribe()` 订阅、`set(field, value)` 写（内部走 `remote.settings.mutate`，宿主串行化）。
- 数据落在 `~/.dsh/settings.yaml`，与 `ui-theme`、`ui-locale` 等同一个文档；同一台机器上所有 DSH 客户端读到同一份。

## 设计

| 项 | 做法 |
| --- | --- |
| Host 侧（`index.js`） | 导出 schemastery `Config`：`{ document: string, schemes: string }`，并在 `apply` 里 `settings.configure({ auto: false })` |
| 字段为什么是字符串 | 配置字段会随版本演进（三轮加了 `storage` / `arrange` / `relocate` / `rules` / `sync`）；若每次都在 schema 里展开，一旦校验失败整节配置会被宿主丢弃，正是最伤用户的情况。客户端本来就有 `normalizeConfig` 做权威校验（夹取数值、丢弃非法枚举），schema 只做「字符串 + 长度」粗校验，复合校验留在唯一事实源 |
| 读 | 启动 `bindHostForm(ctx)`：拿表单 → 订阅 → 立即消费一次快照；`status === 'ready'` 才读值 |
| 写 | `schedulePersist` 先写 `localStorage`（界面不等异步），再 `hostWrite('document', text)`；方案表在 `writeLayouts` 里同样双写 |
| 回环防护 | `hostLastWritten` 记已写入的字符串，读回到自己写的值直接跳过；`hostWriteChain` 串行化写入 |
| 只读部署 | `snapshot.writable === false` 时不发写请求 |
| 降级 | `configForms` 服务不在场（老宿主 / 精简部署）→ `hostForm = null`，全程走 `localStorage`，行为与改造前一致 |
| 坏数据 | 宿主里的 JSON 解析失败 → 保留当前配置与方案表，只告警，不清空界面 |

## 依赖与装载

- `index.js` 需要 `@deepseek-ai/schemastery`。插件以软链接装在 profile 的 `node_modules/dsh-layout` → `E:\dsh-layout`，Node 从**真实路径**解析依赖，所以必须把依赖装到插件自己的 `node_modules`（`pnpm install`，已被 `.gitignore` 忽略），并在 `package.json` 里声明 `dependencies`。实测裸模名从 `E:\dsh-layout` 解析在安装前是 `ERR_MODULE_NOT_FOUND`，安装后 `import('file:///E:/dsh-layout/index.js')` 成功导出 `Config / LAYOUT_SETTINGS_NAMESPACE / apply`。
- `client.js` 的 `inject` 增加 `configForms`（宿主的注入名字符串数组，客户端 loader 的 `optionalStringArray` 只接受字符串数组，写成对象会被判非法）。
- Host 侧改动需要**重启 DSH** 才能加载：宿主进程启动时读插件行，运行中新增的 `Config` 不会被现有进程识别。

## 验证

### 已验证

- 依赖与装载：`pnpm install` 后 `index.js` 可从真实路径导入并导出三个成员；`client.js` 语法通过。
- `configForms` 注入：`inject` 加上 `configForms` 后客户端能取到服务（探针 `forms: true`）。
- 改造前状态确认：未重启宿主时 `configForms.get('layout')` 拿到表单但 `status: 'loading'`、`namespaces: []`——宿主尚未声明 `layout` 节，正是「必须重启」的证据。

### 待重启后验证（本文件在重启后补实测结论）

1. 重启 DSH → 打开页面，探针显示 `status: 'ready'`、`namespaces` 含 `layout`、`writable: true`。
2. 改一处布局（如侧栏宽度）→ 等 250ms 防抖 + 宿主写盘 → 检查 `~/.dsh/settings.yaml` 出现 `layout:` 节且 `document` 含新宽度。
3. 清空该浏览器的 `localStorage`（模拟换浏览器）→ 刷新 → 布局仍是改后的值（从宿主读回）。
4. 存一套方案 → 同样清 `localStorage` → 刷新后方案表仍在。
5. 宿主服务关闭 / 不可用（降级路径）：临时让 `configForms` 不返回表单，界面仍可用、配置仍写 `localStorage`。

## 风险

- 宿主设置文档是**单一文档**：`layout` 节 16 KB 左右的 JSON 字符串会和其他插件配置共用一份文件，写入走宿主串行化，不会互相破坏，但文档整体变大。
- 配置里可能含宿主当前不存在的条目（如某插件的面板），跨机器恢复后这些条目按既有降级逻辑处理（只列出、样式不生效）。
- `schemastery` 是新增依赖（已按规范声明并说明理由）：必须用它定义 Host 侧 `Config`，没有替代写法。
- 重启前写入的 `localStorage` 配置不会被自动迁移到宿主：首次重启后以 localStorage 为准再写一次宿主（因为启动时先读缓存渲染，随后 `schedulePersist` 会在下一次配置变更时双写）。若用户重启后立刻换浏览器且没改过任何设置，旧配置不会带过去——首次写入时机需要实测确认，必要时在绑定宿主成功后主动写一次。
