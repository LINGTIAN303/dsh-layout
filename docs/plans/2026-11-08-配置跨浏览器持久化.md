# 配置跨浏览器持久化

## 目标

布局配置与布局方案原来只存在浏览器 `localStorage`。换浏览器、换 Web 端、清缓存就全部丢失——用户辛苦调好的界面直接归零。改为存进**宿主设置文档**（`~/.dsh/settings.yaml` 的 `layout` 节），跟着 DSH 安装走；`localStorage` 降级为渲染缓存。

## 结论与依据

宿主有三条持久化通道，只有一条能带上配置：

| 通道 | 可用性 | 结论 |
| --- | --- | --- |
| `localStorage` | 一直在用 | 换浏览器即丢，正是要解决的问题 |
| `ctx.get('fs')`（Host 文件系统） | 仅 Host 侧、且需宿主授权根目录 | 客户端插件拿不到，且要自己管路径与并发写 |
| `ctx.configForms`（宿主设置表单） | UI 插件通用通道 | **采用**：宿主负责落盘与并发，客户端只读写字段 |

### 落盘位置：不是 settings.yaml，是 profile 的 cordis.patch.yml

排查时先踩过一个坑：本机有一份 `D:\deepseek-harness` 源码，但那是**已停滞的旧版本**，按它得出的结论（配置写 `~/.dsh/settings.yaml`）是错的。正确的依据只能是从当前 `D:\DSH\resources\app.asar` 解出来的包：

- `@deepseek-ai/dsh-settings` 的 `SettingsForms.write()` 走 `configEditor.edit(entry, …)` —— 写入的是**当前 profile 的 `cordis.patch.yml`**（`PROFILE_PATCH_FILENAME`）。旧 `settings.yaml` 只剩一次性导入迁移，导入后改名为 `settings.yaml.imported`。
- 同一处还要求字段带 **`.volatile()`**：`isVolatilePath(schema, path)` 不通过就抛 `Config field "…" is not volatile`。没有这个标记，客户端写入会全部被拒。

`configForms` 的读取机制（读当前版本源码确认）：

- Host 侧插件导出 schemastery `Config` 并在 `apply` 里 `ctx.settings.configure({ auto: false }, ctx.fiber)`，宿主就把它纳入可编辑设置；命名空间即**插件行 id**，本插件是 `layout`。
- `describe()` 只列出满足三个条件的条目：有 schema、`entry.fiber.state === 2`（已挂载）、`volatileForm(schema)` 非空。
- Client 侧 `ctx.configForms.get('layout')` 拿到 `ConfigFormController`：`getSnapshot()` 读（`{ status, value, writable, revision }`）、`subscribe()` 订阅、`set(field, value)` 写（内部走 `remote.settings.mutate`，宿主串行化）。
- 客户端能取到 `configForms` 的前提是把服务名写进 `inject`；且客户端 loader 的 `optionalStringArray` 只接受**字符串数组**，写成 `{ required, optional }` 对象会被判非法。

## 设计

| 项 | 做法 |
| --- | --- |
| Host 侧（`index.js`） | 导出 schemastery `Config`：`{ document: string, schemes: string }`，并在 `apply` 里 `settings.configure({ auto: false })` |
| 字段为什么是字符串 | 配置字段会随版本演进（三轮加了 `storage` / `arrange` / `relocate` / `rules` / `sync`）；若每次都在 schema 里展开，一旦校验失败整节配置会被宿主丢弃，正是最伤用户的情况。客户端本来就有 `normalizeConfig` 做权威校验（夹取数值、丢弃非法枚举），schema 只做「字符串 + 长度」粗校验，复合校验留在唯一事实源 |
| 读 | 启动 `bindHostForm(ctx)`：拿表单 → 订阅 → 立即消费一次快照；`status === 'ready'` 才读值 |
| 写 | `schedulePersist` 先写 `localStorage`（界面不等异步），再 `hostWrite('document', text)`；方案表在 `writeLayouts` 里同样双写 |
| 回环防护 | `hostLastWritten` 记已写入的字符串，读回到自己写的值直接跳过；`hostWriteChain` 串行化写入 |
| 只读部署 | `snapshot.writable === false` 时不发写请求 |
| 降级 | `configForms` 服务不在场（老宿主 / 精简部署）→ `hostForm = null`，全程走 `localStorage`，行为与改造前一致 |
| 坏数据 | 宿主里的 JSON 解析失败 → 保留当前配置与方案表，只告警，不清空界面 |

## 依赖与装载

- `index.js` 需要 `@deepseek-ai/schemastery`。插件以软链接装在 profile 的 `node_modules/dsh-layout` → `E:\dsh-layout`，Node 从**真实路径**解析依赖，所以必须把依赖装到插件自己的 `node_modules`（`pnpm install`，已被 `.gitignore` 忽略），并在 `package.json` 里声明 `dependencies`。实测裸模名从 `E:\dsh-layout` 解析在安装前是 `ERR_MODULE_NOT_FOUND`，安装后 `import('file:///E:/dsh-layout/index.js')` 成功导出 `Config / LAYOUT_SETTINGS_NAMESPACE / apply`。
- `client.js` 的 `inject` 增加 `configForms`（宿主的注入名字符串数组，客户端 loader 的 `optionalStringArray` 只接受字符串数组，写成对象会被判非法）。
- Host 侧改动需要**重启 DSH** 才能加载：宿主进程启动时读插件行，运行中新增的 `Config` 不会被现有进程识别。

## 验证

### 已验证（真机实测）

1. **落盘成功**：重启宿主后，`~/.dsh/profiles/desktop/cordis.patch.yml` 出现本插件的配置节：

   ```yaml
   - id: layout
     name: dsh-layout
     config:
       document: '{"version":1,"enabled":false,"columns":{…"sidebarWidth":280,"rightbarWidth":520…},"storage":{…},"rules":[]}'
       schemes: '{"active":"scheme-mw856kul-1","list":[{"id":"scheme-mw856kul-1","name":"方案 1",…}]}'
   ```

   解析确认：`enabled=false`、`sidebarWidth=280`、`rightbarWidth=520`、`storage.headerUtilities` 为空、`rules` 为空——与浏览器当时的状态一致；`schemes` 里带着存过的「方案 1」。该文件是宿主每次启动都会应用的 profile patch，**与浏览器无关**。
2. **只有一节**：文件里 `- id: layout` 恰好 1 处，重复写入没有叠加。
3. **迁移生效**：宿主该字段为空时，客户端把本地缓存推上去（首次写入即这次落盘）。
4. **依赖与装载**：软链接安装下裸模块名从 `E:\dsh-layout` 解析不到（`ERR_MODULE_NOT_FOUND`），`pnpm install` 装到插件本地后 `import('file:///E:/dsh-layout/index.js')` 成功导出 `Config / LAYOUT_SETTINGS_NAMESPACE / apply`；`Config.dict.document.meta.volatile === true` 已确认。
5. **bundle 前提**：`dsh-layout` 在 profile 的 `dsh.profile.bundles` 里（51 项中），`dsh.bundle.patch` 指向存在的 `cordis.patch.yml`，无 `platforms` / `engines.dsh` / dsh peer 限制 → 不会被跳过。

### 未能验证

- **换浏览器实测**：DSH Web 端点要求带鉴权的 URL（`dsh web authentication required; reopen the URL printed by dsh web`），我这边只能用无 token 的地址打开，拿不到已授权的浏览器上下文。已落盘的 profile patch 与浏览器无关，等价证据成立，但「另一个浏览器打开后界面自动是同一套布局」这条端到端画面没有实拍。
- **只读部署**：`writable === false` 时不写这条分支由代码保证，未构造只读环境实测。

## 风险

- profile patch 是**整份文件**：`document` + `schemes` 各是一行 JSON 字符串（长句会被 YAML 折行），与本 profile 其他 23 个条目共用一份文件。写入走宿主 `configEditor.edit` 串行化，不会互相破坏，但文件会变长（当前 89 KB，其中本插件约占 6 KB）。
- Host 侧改动需要**重启 DSH** 才生效：宿主进程启动时读取插件行与 `Config`，运行中不会重新识别。
- 配置里可能含宿主当前不存在的条目（如某插件的面板），跨机器恢复后按既有降级逻辑处理（只列出、样式不生效）。
- `schemastery` 是新增依赖（已按规范声明并说明理由）：Host 侧 `Config` 必须用它定义，没有替代写法。
- 首次升级后如果宿主字段为空、而浏览器缓存也恰好为空，则不会有内容可迁移——此时以默认配置开始，属预期。
