# 布局引擎（Client）

对应源码：`client.js`。本文只写设计决策、约束与踩坑，不重复代码逐行说明。

## 为什么是「注解 + CSS 覆盖」

宿主 Web 外壳（ui-layout 的 AppFrame）在 `root` 单插槽里渲染三栏网格，列宽由 React inline style 的 `grid-template-columns` 决定，右栏与设置面板各有自己的定位规则。要改布局有三种路径：

1. 替换 `root` 插槽：必须重写三栏、抽屉、拖拽手柄、主题呈现，还会让其它插件依赖的子插槽全部重建 —— 影响面过大。
2. 写宿主 inline style：React 下次渲染会覆盖，且与宿主拖拽逻辑打架 —— 不稳定。
3. 给宿主 DOM 打标记 + 生成带 `!important` 的覆盖样式：不接手宿主逻辑，只覆盖几何；样式移除即恢复默认。

本插件选 3。代价是依赖宿主 DOM 结构，因此专门做了「识别不到就不动手」的降级。

## 注解器

每一轮识别产出一个 `targets` 对象：框架元素、四个区域元素、侧栏根、五个侧栏块、面板行、会话内容容器、设置面板，以及各区域的拆解单元（`convParts` / `sidebarParts` / `rightbarParts` / `settingsParts`）。标记规则：

| 标记 | 落在 | 用途 |
| --- | --- | --- |
| `data-dshl-frame` | `#root > [data-slot="root"] > div` | 网格覆盖与拖拽手柄的坐标基准 |
| `data-dshl-region="sidebar|center|rightbar|bottom"` | 框架的四个网格子项 | 列宽、列序、显隐 |
| `data-dshl-sidebar` | `[data-slot="sidebar"]` 的第一个子元素 | 侧栏块排序容器 |
| `data-dshl-block="brand|new-session|panels|workspaces|footer"` | 侧栏根的直接子元素 | 块排序/隐藏 |
| `data-dshl-panel="<aria-label>"` | 面板导航行的直接子元素 | 面板排序/隐藏；属性值即面板显示名 |
| `data-dshl-conv` | `[data-conversation-content]` | 会话内容宽度变量 |
| `data-dshl-settings` | `[data-shortcut-modal="settings"]` | 设置面板尺寸/位置 |
| `data-dshl-unit="<单元 id>"` | 声明表 `PART_UNITS` 里登记的拆解单元 | 单元显隐与位置；id 同时是配置路径与覆盖度的键 |
| `data-dshl-convroot/convbody/convscroll`、`data-dshl-rbhost`、`data-dshl-setpanel` | 换序 / 命名网格所需的「结构容器」 | 只被结构规则引用，不是可隐藏单元 |

块分类不依赖 CSS module 类名，按结构判断：`NAV` 是面板导航、`BUTTON` 是新建会话、含 `[data-sidebar-toggle]` 的是品牌行、含 `[data-slot="sidebar.workspaces"]` 或 `role="tree"` 的是工作区、含 `[data-slot="sidebar.settings"]` 的是底部操作；兜底把第一个未分类子元素当品牌行。

## 网格覆盖与状态门控

宿主的列宽由它自己的 store 计算，且随侧栏折叠、右栏开关、窗口宽度变化。覆盖样式不能是「一个固定模板」，必须按宿主状态门控：

- `@media (min-width: 768px)`：窄屏抽屉形态完全交给宿主。
- `:not([data-sidebar-collapsed])`：折叠态沿用宿主轨道宽度（56px 或平台差异），本插件不掺和折叠动画。
- `[data-rightbar-collapsed]`：右栏收起时把右栏轨道写成 `0px`，避免无故占位。
- 列序通过给各区域写 `grid-column: 序号` 实现；轨道模板按配置的列序逐列拼接，中栏始终 `minmax(最小宽, 1fr)`。

宿主自带的两个拖拽手柄（`[data-side]`）在启用自定义布局后被隐藏：它们的 `left` 由宿主列宽算出，与本插件改动后的列宽不一致；改由浮层里的 `dshl-drag` 手柄接管，拖动时实时写配置。

## 右栏的坑

右栏占位在框架网格里，但面板本身是 `position:absolute; right:0` 的独立元素，宽度来自它的 inline style，并且同时写 `--dsh-sidebar-width`。因此只改网格轨道不够：

- 宽度：同时覆盖 `width`、`max-width` 与 `--dsh-sidebar-width`，否则面板仍按旧宽度绘制。
- 位置：右栏排到第一列时（左栏右置），面板补 `right:auto; left:0`，否则会停在窗口右边而不是它所在列。

## 设置页与命名网格的坑

设置面板用 `grid-template-areas` 摆四个子级（`"title header" / "nav options"`）。拆解时有两个陷阱：

- 只改 `grid-template-columns` 会留下空轨道：隐藏导航后左列照样占 188px。必须成对重写 `grid-template-areas` 并给每个子级重新指派 `grid-area`。
- 折叠成单行时必须同时重写 `grid-template-rows`：宿主写的是两条轨道（`54px` + 剩余高度），只把列改成一列，内容仍只占上半截，下半截留空。实测改成 `minmax(0,1fr)` 后内容铺满。

会话头也有同类问题：宿主写死 `grid-template-rows: 32px 35px` 与 `min-height: 76px`，隐藏一行要同时把行高交还 `auto`、撤掉 `min-height`，否则高度不变。

需要交换会话头的两行时不能用 `order`：会话头是两列网格（第一列 0px 的 leading），`order` 会让项落进 0px 列。改用显式 `grid-column` / `grid-row` 定位。

## 会话区宽度

`[data-conversation-content]` 上的 `--dsh-chat-content-width` 同时决定消息列宽与输入卡宽度（输入卡另有 `--dsh-composer-card-max-width`）。覆盖值写成 `min(<配置像素>, 100%)`：右栏展开把中栏压窄时，固定像素会导致内容横向溢出。

## 设置面板

设置面板是 `position:fixed` 遮罩里的 flex 居中子项，默认 800×684、左导航 188px。覆盖方式：宽/高直接给 `!important`（高度再套 `min(配置, 100vh-48px)`）、导航宽度改 `grid-template-columns`、偏移用 `position:relative` + `left/top`（相对定位不改变父级居中布局，因此偏移量是相对默认位置）。

## 不可恢复状态的防护

插件能隐藏的每一项，都可能是用户回到插件详情页的通路。判断标准只有一条：**任何配置组合都不能让「恢复」本身也变成不可达**。

- **风险判定**（浮层组件内实时计算）：`hideSidebar`、隐藏任一面板行、隐藏全部侧栏区块、实测侧栏列不可见（宽度 <40、完全在视口外）或面板行全部不可见、**中栏（main 面板，插件详情页所在列）宽度不足 120px 或完全在视口外**，任一成立即视为风险，常驻恢复按钮。中栏条件覆盖「侧栏+右栏轨道把中栏挤出屏幕」的组合。
- **恢复按钮**放在 `shell.overlay` 的 fixed 定位层，不依赖被改动的三栏；自由模式下点击只打开编辑浮层、不直接改配置（避免误触）；空白模式才给出会改配置的按钮。
- **两条独立键盘通道**：`Ctrl/⌘+Alt+L` 打开编辑面板（注册到宿主快捷键服务，失败则退回 window 监听）；`Ctrl/⌘+Alt+Shift+L` 直接 `replaceConfig(null)`，不经过 React 渲染。
- **Web 哈希通道**：`#dsh-layout=reset` 在加载/哈希变化时直接恢复默认并清掉哈希。
- **设置面板偏移夹取**：以「面板完整留在视口内」为约束反算允许偏移，滑块值只是意图，最终生效值在样式生成时夹取。
- **折叠态门控**：所有列序/轨道规则都限定 `:not([data-sidebar-collapsed])`。实测过不加门控的后果：宿主 902px 窗口自动折叠成 56px 轨道，而本插件仍按自定义列序把侧栏排到第 3 列，侧栏落到 x=902 视口外——这类错位本身就是一种不可恢复，必须由门控消除。
- **恢复按钮的可点性**：浮层根 `.dshl-editLayer` 故意 `pointer-events:none`（不挡会话），所有可点子元素必须显式声明 `pointer-events:auto`。工具栏声明了，恢复按钮漏了，于是按钮继承了 `none`：看得见、点不到（`elementFromPoint` 命中的是下层会话）。修复为三层：按钮显式 `pointer-events:auto`、内联 style 再兜一层、以及 document 捕获阶段的 `pointerdown/mousedown` 坐标命中兜底——即使样式/层叠/热更新残留导致按钮无法命中，点击它所在的矩形也会打开浮层。
- **模块热更新去重**：客户端模块重新执行 `apply` 时，先清掉上一代 `style[data-dsh-layout]`，避免旧的 `pointer-events:none` 规则压住新规则；本代自己的两个标签保持复用，不让每次重绘重建样式。
- **工具栏宽度**：窄窗口下按钮不换行会挤成两行字形；`flex-wrap` + `white-space:nowrap` 保证工具条在 1000px 左右仍可读。

## 恢复按钮的落点（依附 / 留白 / 空白 / 角落）

恢复入口不能固定钉在一个位置：钉住了就长期占用一块可用区域，还可能压住别的内容。做法是把「落点」当成一次测量结果。

**通用性前提**：插件不是原生的，用户随时可能装一个新插件，它的控件位置我不知道。所以落点算法**不认识任何具体插件**——不匹配类名、不匹配 `data-slot`、不关心框架。它只用浏览器提供的通用事实：元素矩形、是否可见、是否可交互。任何插件把控件放在哪里，都只是「一个矩形」，算法一视同仁。这条约束决定了下面所有规则都不许出现宿主或第三方插件的具体标识。

- **整页测量**（`surveyPage`）：遍历 `document.body` 而不是四个列区域。插件可以把界面渲染到 overlay、portal、body 直下，只扫列区域会完全看不见它们。产出两份数据：全部可见可交互元素的矩形（占位），以及宽度不超过视口 60% 的锚点列表。
- **矩形碰撞**（`collidesRects`）：候选位置必须与所有占位矩形零相交（含 6px 呼吸空间）。早期用 `elementFromPoint` 九点采样会从药丸形按钮的圆角和两个控件的窄缝里漏过去，表现为按钮边缘压住输入框；矩形比较是精确的，且一次遍历就够。
- **依附优先**（`anchorCandidates`）：贴在某个锚点控件的旁侧，视觉上像「那一排多了一个按钮」。规则：
  - 同排判定只看中心 y 差 <12，**不看父容器**——跨插件、跨容器的同排控件会被正确归到一起；
  - 一排的左右跨度就是可视工具栏范围，依附点必须落在跨度内，否则会飘到工具栏外侧、像挂在卡片外的异物（这是实测第一版就踩到的坑）；
  - 只有落在真正「缝」里（两侧都有控件）得分最高；纵向贴靠容易落进正文，只在没有同排伙伴时才允许；
  - 只在高分候选里随机，避免每次都贴同一控件。
- **留白兜底**（第二优先）：没有可用锚点时，在可见区域网格里用矩形碰撞筛出干净点，四方向步进算留白分，取最优一批随机。
- **空白页**：四个区域全不可见 → `mode:'blank'`，屏幕正中给「恢复默认 / 插件页 / 编辑模式」三枚按钮 + 快捷键提示；此时不存在「空位」概念，位置必须确定且醒目。
  - 「插件页」不是简单切面板：插件详情页渲染在 `main` 面板里，空白模式意味着 `hideCenter` 为真，直接切过去只会得到又一片空白。所以它先释放 `hideCenter`，再 `ctx.layout.selectPanel('plugins')`。
  - 「编辑模式」在空白页确实没有区域可框，所以工具栏显示「当前没有可见区域可拖拽，用预设或恢复默认」，而不是给一个看着像坏了的空浮层。
- **角落**：一点干净位置都没有 → 左下角固定位，绝不让入口消失。

**遮挡守卫（对应「未知插件」）**：落点只在界面变化时重算还不够——用户新装的插件、动态弹出的挂件都可能出现在按钮之后。所以 `refresh` 之外另有一个 MutationObserver：DOM 变化 600ms 后检查按钮矩形是否压住可交互元素，是则 `requestReposition()` 递增 store 里的 `reposition` 信号，让落点重算。带 1200ms 最小间隔，避免界面高频变动时按钮满屏跳。实测：注入一个第三方风格的悬浮控件覆盖按钮 → 约 2 秒内按钮自行移到另一处（附着到「分支」按钮旁），重叠消失。

## 识别层看见的是哪一层

识别层不是「知道整个应用的界面模型」，而是在每一轮 `readTargets` 里读**此刻渲染在 DOM 里、有布局的那一层**：

- 会话区只在会话页可见时才有 `conversation.header/session/composer` 三个槽位；右栏收起或不在会话页时 `readRightbarParts` 返回 `null`；设置面板是 `body` 下的弹层，只在打开时存在。
- 插件详情页上，唯一常驻可识的是三栏骨架和左侧栏的 4 个单元；其余 20 个官方单元此刻都不在 DOM 里。
- 所以「声明表 + 快照」缺一不可：声明表（`PART_UNITS`）提供离线结构知识，快照（`area-snapshots/v1`）提供「上次观测到的单元与时间」。覆盖度第三态不再是含糊的「当前为空」，而是「上次观测 / 上次未出现 / 从未识别 / 无快照」。
- 快照只记 `{ at, ids }`：单元 id 与覆盖度判定同一套（`kind:order` 用 `needs` 推、`targets` 复合项按声明 id 记），回放时能直接对上；不存元素引用，避免离开页面后持有已卸载节点。

## 编辑面板为什么渲染到 body

面板最初放在 `shell.overlay` 里，结果被设置弹层整层盖住：设置弹层的祖先 `.overlayLayer` 是 `position:absolute; z-index:20` 的堆叠上下文，面板再高的 `z-index` 也升不出这一层；而设置弹层是 `body` 下的 `position:fixed; z-index:1000`。

因此面板用 `react-dom` 的 `createPortal` 渲染到 `document.body`（宿主未提供 `react-dom` 时退回原地渲染，功能降级但不崩）。面板根节点标 `data-dshl-layer`，既让恢复按钮的遮挡探测忽略它，也保证面板内容在被 `inert` 的 `#root` 之外仍可点击——实测设置弹层打开时，面板里的开关照常生效。

Esc 处理要排除面板自身：`document.querySelector('[role="dialog"]:not(.dshl-panel)')` 存在时说明宿主弹层在场，Esc 交给它，不误关面板。

### 快捷键只开面板，不进编辑模式

`Ctrl/⌘+Alt+L` 只调 `openPanel()`。早期版本是 `openPanel() + setEditing(true)`，一次按键同时打开面板并在界面上铺一层可拖的虚线框——面板和编辑模式是**并列的两条工作路径**（一个在浮层里调，一个直接在界面上拖分隔条），叠在一起反而两套交互互相干扰。编辑模式改从面板里的「编辑模式」开关进，或者恢复按钮的空白模式按钮。

`Ctrl/⌘+Alt+Shift+L` 是独立的硬重置通道，`replaceConfig(null)` 直接改配置、不经过 React 渲染，所以即使浮层组件出问题也能恢复。两条通道互不影响，实测连按快捷键不会叠加面板（`panelCount` 恒为 1），也不会清掉用户手动开的编辑模式。

### 面板内部的五段骨架

面板是**非模态浮层**：开着的时候要能边看界面边改，所以没有焦点陷阱，也不加 `aria-modal`——加上会让读屏软件以为背后界面不可交互，而背后恰恰是用户要改的东西。

内部按 flex 竖排五段，只有第 4 段滚动：

| 段 | 类名 | 高度（桌面实测） |
| --- | --- | --- |
| 标题栏 | `dshl-panelHead` | 39 |
| 工具区（开关 + 预设） | `dshl-panelTool` | 75 |
| 分页条 | `dshl-panelTabs` | 38 |
| **正文（唯一滚动区）** | `dshl-panelBody` | 剩余（664 面板 → 466） |
| 底栏（导出/导入） | `dshl-panelFoot` | 45 |

初版是「一整块滚动」，实测滚 400px 后分页条跑到 `y=-210`、导出按钮在 `y=3188`，滚到哪儿都找不到导航。固定前四段之后，滚到哪一页都能切分页、导出配置。

代价是**五段固定部分互相挤占**：197px 是硬开销，往任何一段加东西都会直接压缩正文。窄屏（`≤900px`）改底部抽屉后可用高度只有 `82vh`，正文约占 67%。

分页条按 WAI-ARIA tabs 模式走 roving tabindex：只有激活项 `tabIndex=0`，`←/→` 循环切页、`Home/End` 跳首尾。七个页签全给 `tabIndex=0` 会让键盘用户按七次 Tab 才能越过这一排。

### 七个分页怎么分的

按「用户要回答的问题」分，不按数据结构分。前五页回答「我要改什么」，后两页回答「我改的东西对上了没」：

| 分页 | 回答的问题 | 正文屏数 |
| --- | --- | --- |
| 布局结构 | 三栏骨架、底部条、命名方案 | 1.4 |
| 侧栏 | 侧栏内部区块与面板导航的排序显隐 | 1.6 |
| 入口收纳 | 把不常用的入口收进「更多」 | 3.0 |
| 区域拆解 | 会话区 / 右栏 / 设置页内部拆解与尺寸 | 3.2 |
| 槽位编排 | 容器排列、区域搬移、联动规则 | 2.1 |
| 识别诊断 | 宿主原生界面到手了什么、配置生效没 | 3.2 |
| 插件与槽位 | 第三方插件贡献了什么、能改动哪些 | 3.1 |

第六、七页原先是同一页（「识别与外部」），**7.8 屏、占全部内容 35%**。它装了三件互不相干的事，且「拆解覆盖」一张卡里上半是 24 行只读状态、下半是带 24 个控件的可操作单元，混在一起用户分不清哪些能点。拆开后最大值降到 3.2 屏。

拆解覆盖的 24 行只读状态做成可折叠：默认按「有没有异常」决定展开（任一区是「从未识别 / 上次未出现」就自动展开），全绿时收成一行汇总 114px——24 行全绿没有任何信息量。

**页签宽度是硬约束**：七个页签实测 448px、可用 456px，只剩 8px。改任何页签名之前先量一次总宽。已加 `overflow-x:auto` 兜底（隐藏滚动条），窄屏 774px 实测全放下。

外壳底色必须比卡片暗：外壳 `bg-layer-2`（`#2c2c2e`）、卡片 `bg-layer-1`（`#232324`），跟宿主设置弹层一致。初版外壳用了 `bg-overlay`，那是 `#61666b` 的中灰——宿主拿它做弹出层底色，不是浮层容器，套上去层次整个倒过来。

## 插件来源：注册表 + fiber
几何扫描只能回答「这块看起来像什么」，回答不了「这是谁注册的什么」。宿主 slots 服务能回答后者：

- `ctx.get('slots')` 实测可用，`snapshot()` 返回完整槽位树（112 个槽位），`entries(key)` 给出条目的 `id / order / registrant / component`。这两个方法不在服务声明的 `register / registerFactory / inject` 里，属于内部接口，所以整块包在 try/catch 里，拿不到就让卡片显示降级说明。
- 注册表只给组件函数引用，不给 DOM。定位靠 fiber：从 `#root` 和 body 直接子级里的每个 `__reactContainer$` 出发遍历整棵树，用 `fiber.type === entry.component` 做同一性匹配。**不要用组件名**：实测生产构建里名字可能被压缩（`Mn/$4/z4`）甚至为空（`dsh-context` 的图标），但函数引用匹配照样能命中（62 个目标命中 37 个，未命中的全是当前没渲染的）。
- 命中的节点常常是纯图标（侧栏面板图标是 `svg`）。操作目标要上探：svg → div → span → button，最多 5 层，落到 `button / a / [role=button|tab|menuitem|switch] / label / li` 上，排序与隐藏才有意义。
- 一个组件可能渲染多个顶层节点（Fragment）：隐藏时全部标记，排序时只在「只有一个顶层节点」时才开放，否则 `order` 无法表达。
- 设置弹层是 body 下的独立 React 根（body 上有 3 个 `__reactContainer$`）。只遍历 `#root` 会漏掉弹层：修复前设置页 21 个 section 全部显示「未渲染」，修复后 `settings.section.icon` 7/7、`settings.section` 1/21（内容区只挂载当前 section）都能定位。
- 分级沿用「入口不隐藏」的原则：列表里非入口项可隐藏 + 排序；入口类只排序；`main` 页面、单槽、弹层类（渲染结果含 `role=dialog/menu/listbox`）只读。`dsh-layout` 自己的条目直接排除，避免自己操作自己。
- 扫描结果缓存 1.5 秒（整树 fiber 遍历 + 全槽位 entries 不适合每 120ms 跑一次）；卡片与样式只依赖 `slotSources.version` 进识别签名，扫描结果变化才重绘。
- 服务或 fiber 任一路失效：卡片退化为「不可用」说明，页面内部的两层几何拆解不受影响。

### 清单的搜索与排序

- **搜索**是本地过滤：命中槽位键、条目 id、注册者、组件名。槽位键命中时整组保留（搜 `sidebar` 要看到该槽位的全部条目，而不是空组标题）；条目不命中就只剩命中行。不做模糊匹配——id 本身就是精确串，模糊会让 `dsh-context` 与 `dsh-context-xxx` 混在一起。
- **顺序语义**：清单显示的必须是界面上真实的顺序。宿主按「条目 order 升序、同值按注册顺序」摆放，而配置里的 `slots.order` 通过 CSS `order` 覆盖。所以清单排序键是「配置覆盖值 ?? 宿主 order」，同值按注册序兜底。
- **写回为什么用 0..n-1**：条目初始 order 由宿主注册优先级决定（可能全是 0，也可能不连续），在旧值上 ±1 会出现「同值后由注册序兜底」→ 点了箭头视觉不动。改成把整组按新序列重新编号 0..n-1，顺序完全由配置表达，也顺带让下一次读取稳定。
- **两条入口一套链路**：拖拽（`dragstart` 记录条目、`drop` 记录目标）与箭头（与相邻行交换）都调用 `moveItem(group, fromId, toId)`，再进 `applySequence` 写序号。两套实现各写一份顺序逻辑，必然漂移。
- **跨槽位不生效**：顺序键按 `槽位::条目` 分开，拖动只在自己分组内换位；跨组拖拽没有语义（不同槽位互不排队）。
- **与面板导航同步**：`sidebar.panellist` 的顺序同时是面板导航的顺序（面板顺序存显示名）。开着同步时，拖拽后按链接表把新序列写成 `sidebar.panelOrder`。

## 槽位编排：排列为什么要换容器

排列不是给条目加一条属性，而是换容器：容器不改，条目再怎么 `order` 也排不出列。

- **`order` 不够用**：`order` 只在 flex / grid 容器里生效。侧栏面板导航是 `flex-direction:column`，改成列宽没处写；槽位出口是 `display:contents`，根本没有自己的布局盒；右栏标签栏与设置页导航各有自己的布局。要并排多列，必须先把容器变成网格容器，列宽、行距、换行才有一处可写的地方。
- **网格是最小表达**：`display:grid` + `repeat(N, minmax(0,1fr))` + `gap` 三件套同时解决等宽、间距与换行；行内补 `min-width:0`，否则长文字会把 `1fr` 列撑破（实测「自媒体工作台」在 128px 列里靠宿主自带的省略号收住）。
- **容器有两个来源**：已知布局容器（注解器认出的侧栏面板导航、侧栏底部、右栏标签栏、设置页导航）与列表槽位出口（≥2 个已渲染条目的最近公共父级，id 形如 `slot:<槽位键>`）。同一节点只算一次，已知容器优先。
- **已知容器要往下穿一层**：注解器给出的块元素常常只是外壳——设置页的导航列 `nav` 里只有一个 `navList`，真正装条目的是内层列表。容器解析时穿过「只有一个子元素」的包裹，最多 4 层；实测 `settings-nav` 由此落到 `navList`（21 个导航行），2 列才有意义。
- **过滤比枚举重要**：浮层/菜单/弹层类槽位（`overlay|contextmenu|menu|popover|tooltip|dialog|toast`）的条目互相覆盖，排成网格没有意义；零尺寸或 `display:none` 的容器排了也看不见，不列进清单。`display:contents` 的出口按第一个有尺寸的子元素判断可见性。
- **「只留图标」用结构位置，不用类名**：侧栏面板行的结构是「图标 + 文字」，隐藏行内第二个子元素即可；但这条只对 `panels` 开放——其它容器第二个子元素可能是控件，误藏会断功能。`compact` 属于「知道结构」的容器，不是通用规则。
- **不在场也能调**：已配置但当前不可见的容器（设置页没打开时的 `settings-nav`）仍在卡片里标「此刻不在场」，可以改或复位；容器出现/消失进识别签名，卡片跟着重绘。
- **可恢复性**：排列只生成 `display` / `grid-template-columns` / `gap` / `min-width` / 居中这类可逆声明；清空配置、关掉「启用自定义布局」时整段动态样式消失，宿主布局原样回来。实测面板导航 2 列时 10 行并成 5 行、378px 收到 212px；复位后 NAV 回 `flex`、378px，动态样式里不再有 arrange 规则。

## 区域搬移：为什么是「投影」

跨区域搬移（例：把侧栏品牌行搬进设置页）看起来只要移动 DOM 节点，实际三条路都不通，最后选的是「不动物件树、只改看见的位置」：

1. **在目标处把宿主槽位再渲染一份**：宿主 slots 核心规定子槽位 key 全局独占声明（`SlotCore.register` 对已声明的 children key 直接抛 `already declared`），`renderSlot` 也只发给声明它的那个条目。拿不到别人的槽位。
2. **改条目 order / 让宿主挪位**：宿主没有 update/move 接口，order 只在注册时参与一次排序，改序只能 dispose 后重注册，而 disposer 在注册者手里。
3. **真搬 DOM 节点**：React 18.3.1 把合成事件委托挂在 `createRoot` 的容器上；节点被搬到别处后，宿主列表一增删同级条目，commit 阶段就会 `insertBefore/removeChild` 失败（`NotFoundError`），而且搬出容器后事件直接失效。对「插件永远可恢复」的定位来说这是不可接受的整树崩溃风险。

投影的做法把「位置」和「结构」拆开：

- 源节点留在原 React 树里，只加 `data-dshl-teleport` 让 CSS 把它变成 `position:fixed`（`z-index:1100`：高于设置弹层 1000、低于编辑面板 1250）。事件委托、Store 订阅、宿主逻辑全都不受影响。
- 落位由**用户画的框**给出：框的左上是落位坐标，框宽是宽度（见下节「框：位置由用户指出」）。
- 对齐靠帧循环：量一次真实矩形，按「框的位置 − 节点矩形」补 `--dshl-tx/--dshl-ty` 位移；差值收敛到 0.5px 内停帧，最多追 120 帧。
- 源节点被 React 重建时下一轮识别会重建投影；移除配置、关闭插件时内联变量一并清掉，不留下空的 `style` 属性。

## 框：位置由用户指出（第十六轮）

前五轮的机制是「源 × 目标容器 × 开头/结尾」：

```
源 22 × 目标 18 × 位置 2 = 792 种组合
```

形状兼容（第十一轮）、链式剔除（第十二轮）、窗口栏避让（第十三轮）、槽位化（第十四轮）、槽位方向修正（第十四轮补）全在这个积上做减法，永远补不完。问题不在实现而在抽象层级：**目标容器与位置这两维，在用户能直接用鼠标指出位置的前提下根本不需要建模**。

所以配置里只剩几何：

```js
relocate: { 'block:brand': { frame: { x: 582, y: 310, w: 564 } } }
```

`x/y` 是视口坐标（与投影的 fixed 定位同一坐标系），`w` 是框宽。源高度不存——它是内容的函数。

### 三个判据，全是几何

1. **宽度纠正**：`width = max(框宽, 源原始宽, 120)`。框画窄了不该把内容压没，这是「框不足以容纳源宽高时自动放大」的落地。
2. **视口夹取**：框整体夹进 `[0, innerWidth] × [projectionTopBound(), innerHeight]`，上界避开原生窗口栏。
3. **碰撞迁移**：框与目标容器**内部已被占用的内容**相交时，沿上下左右试「贴到障碍外侧」，按距离由近到远取第一个不相交的；都不行就留在原位并标 `conflict`。

### 目标容器是「落进去的那个区域」，不是障碍物

这一点必须分清，否则整套判定必然错：

- 视口被三栏铺满，**把区域本身当障碍 → 任何位置都碰撞**，迁移永远找不到空位。
- 所以区域是框的**宿主**（`relocateHostOf` 取包含框中心的区域），真正的障碍是区域**内部已被占用的同级内容**。

**障碍层级要自适应**（第十七轮）：宿主不同区域的嵌套深度不一样——侧栏区域下面是 `[data-slot=sidebar]` 再套一层才是真正的块容器。固定取「区域的直接子元素」时，这类区域会退化成一个把整个区域都包住的障碍，框落哪儿都碰撞。

`relocateObstacleLevel` 的下钻规则三条，缺一不可：

1. 某层只有一个实质子级 → 它可能是包裹层，进到它里面看看；
2. 但它必须「几乎撑满父级」（4px 容差）才算包裹层，否则它就是个普通的小内容块；
3. **包含源的那个子级不算包裹层，也不当障碍**——那是源自己所在的块，应当下钻进去找它的兄弟。

第 3 条踩过坑：早先的写法把所有「包含源」的子级都过滤掉，于是源在包裹层里时（宿主侧栏正是这种结构）该层被滤成空数组，函数直接返回「没有障碍」——让位逻辑整个跳过，源就那么盖在内容上。正确的分界是：源的**祖先**继续下钻，源的**自身**才排除。

**区域归属按相交面积**（第十八轮）：早先用「框中心 x + 框底边 y」取命中点，框高跨出区域底沿时（用户从会话区顶部一路往下画）那个点落在所有区域之外，`relocateHostOf` 返回 `null` → 判定成「无宿主」→ 没有障碍物 → 让位整个跳过。改成取与框**相交面积最大**的区域，同时修掉边界失效、也更符合「框主要落在哪」的直觉。

**高度要用「当前实际高度」而不是原始高度**：`relocateResolve` 对已在投影中的源读 `projection.entries` 里记录的实时矩形高度——节点此时已按框宽排过版，实际高度才是它真会占的高度。首次落位时拿不到，才退回原始高度。用错会让「源被改宽后变高、压住下方内容」判不出来。

### 画框的交互（用户实际怎么用）

- 空白处按下拖 → 画新框，松手提交
- **已有框时框内按住拖 → 整体移动**（不必重画）；**拖右边缘 → 改宽度**，二者提交时都不走「放大到源宽」
- 方向键微调 1px、Shift + 方向键 10px、Enter 应用
- Esc / 右键 / 「取消」退出

两个必须避开的坑：

**框外按下不能立刻算「新画」。** 用户只是想挪一下却点偏几像素，旧框就被整个丢掉、回到从零画。所以框外按下先标 `outside` 待命，位移超过 6px 才承认是另画一个，单击则什么都不改。

**进入画框要临时收起编辑面板。** 面板贴在左/右会盖住要画的位置，而画框是「对着真实界面指位置」的操作。但退出时必须恢复它原来的开合状态（`panelBeforeFramer`），否则用户「调整一下」之后面板凭空消失，还得重新找入口。

### 落位影子

拖拽时实时显示两层框：实线是用户画的框，**虚线是自动让位后的真实落点**（两者重合时不画虚线，避免叠一条重线）。用户松手前就知道东西最终会落在哪，不会出现「预览说没事、松手跑掉」。

压暗只由主框的 `box-shadow: 0 0 0 9999px` 承担，且 `:not([data-preview])` 排除影子框——多个框各带 9999px 投影会叠成好几层，越拖越黑。

### 为什么去掉占位符

占位符原本是「让目标容器为源让出高度」的机制，它带来三处必然的复杂性：

- 源高度要反写进占位符高度，两者互相影响 → 帧循环要追 240 帧
- 目标容器自己也被搬走时占位符跟着飞 → 链式剔除
- 目标塌成 0 尺寸时占位符留下一条空白条 → 帧循环里的拆卸守卫

画框之后源**不进入任何容器的布局流**（它本来就是 fixed 投影），让位没有意义——用户已经用框指定了位置。去掉之后三处复杂性同时消失，帧上限从 240 降到 120。

代价说清楚：源压在容器内容上时会盖住内容。这个代价由「碰撞检测 + 向空白让一让」承接，而不是由容器让位承接。

### 位移必须增量累加，不能写绝对坐标

含 `transform` 的祖先会让 `position:fixed` 的 containing block 不是视口——那时 `left:0` 不等于屏幕左边，写绝对坐标会整体偏移一个祖先的位置。累加「还差多少」与基准无关，两种情况都收敛到同一视觉位置。这是保住旧实现正确性的关键一条，重写时不要改成绝对赋值。

### 旧配置保留为「需重画」

旧值是 `{ to, place }`，没有位置信息，换算不出框。不静默丢弃（用户会以为搬移自己消失了），保留成 `{ legacy: true }`：

- 面板上逐条标「需重画」+ 重画按钮
- 顶部一条汇总，可「清空需重画的」

### 多个搬移源互相看不见（第十九轮修）

障碍表来自「区域的子元素矩形」。但同一轮里首次落位的两个源，在 DOM 里都还是各自的原始位置，于是：

```
A 看 B → 在原位，不挡
B 看 A → 在原位，不挡
结果：两个源搬到同一处，谁也不让，直接叠在一起
```

不能指望「下一轮投影后 A 变成 fixed、B 才把它当障碍」来收敛——那是靠副作用的巧合，首帧会先叠一下，而且顺序一变结果就变。

解法：解析时把**本轮其它源的配置框**显式并入障碍表（`peerFrames`）。用配置框而不是解析后的位置，因为解析后的位置依赖本轮结果，拿它当障碍会形成顺序依赖。

### 拖拽预览的性能（第十九轮修）

`evaluate` 在每个 `pointermove` 都跑一遍，而 `relocateObstacles` 要为区域内**每个子元素**做 `getComputedStyle` + `getBoundingClientRect`——都是强制同步布局。一次拖拽几百个事件 = 几百次布局抖动，拖起来会发涩。

解法：障碍表按 host 名缓存（`useRef` 跨渲染保持，host 变了才重算）。障碍只依赖「落在哪个区域」，同一次拖拽里 host 不变。

### 键盘 / 触屏怎么建框（第十九轮补）

原先方向键与 Enter 都要求「已有框」才生效，**唯一的建框方式是拖鼠标**——键盘用户进了画框层就卡死在那里。

补了两条：

| 按键 | 行为 |
| --- | --- |
| 无框时按方向键 | 以源现有矩形为起点生成默认框，并立即按一下方向 |
| `+/=` / `-` | 改宽度（Shift 加大步长） |

「无框」这个状态必须单独处理：它不是错误状态，而是键盘用户唯一的入口。

### 画框的状态机（第二十轮查）

画框是跨多步的过程（进入 → 画/调 → 提交或取消），中途可能被打断。三条路径都要成立：

| 路径 | 行为 |
| --- | --- |
| 进入时面板开着 | 收起面板；退出时还原 |
| 进入时面板关着 | 不动；退出时也不动 |
| 进入后用户按快捷键开了面板 | **退出时保留**，不能吞掉 |

最后一条是修掉的真 bug：早先退出时无条件写 `panel: panelBeforeFramer`，
若进画框时面板本来就关着（`panelBeforeFramer = false`），用户期间自己用 `Ctrl+Alt+L`
打开的面板会在退出瞬间被关掉。正确判据是 `snapshot.ui.panel || panelBeforeFramer`。

### 恢复通道永不被编辑态阻断（第二十轮修）

`Ctrl+Alt+Shift+L` 与 `#dsh-layout=reset` 两条恢复路径原先都不退出画框层。画框层还开着时清空配置，用户会对着一个已清空的界面继续画，画完又写回配置——恢复了等于没恢复。

修法：恢复动作**不检查也不等待**任何编辑态，直接生效，同时把画框层一并收干净。这是安全底线：用户可能正卡在自己调坏的界面上，任何「先退出某模式才能恢复」都是陷阱。

### 键盘事件不要漏给宿主（第二十轮修）

画框层的 keydown 挂在 `window` 捕获阶段。方向键、`Enter`、`+/-` 只做了 `preventDefault` 没做 `stopPropagation`，于是：

- `Enter` 会同时被宿主的会话输入框收到 → 用户以为只是确认了框，消息却发出去了
- 方向键会同时驱动宿主的列表导航 / 光标移动

四个键现在都同时 `preventDefault` + `stopPropagation`。

### 源消失时不要写幽灵配置（第二十轮修）

`FrameLayer` 有「源消失就自动退出」的守卫，但那要等下一轮渲染。`commitFrame` 仍可能在竞争窗口里被走到（画完松手的同时页面切走了）。早先会照样写入一条配置，留下一条永远不生效的搬移——面板标「源单元不在场」，用户以为画成功了。

现在源不在场就什么都不写、直接退出。

### 离线可验证

两个 Node 断言脚本，改动搬移相关函数后先跑它们：

| 脚本 | 覆盖 | 条数 |
| --- | --- | --- |

## 区域搬移（历史）：前五轮为什么不够

下面几节是槽位化时期留下的约束记录，机制本身已被画框取代，但**「窗口栏避让」与「两处安全区下界语义不同」仍然是现行的**，改写投影时必须保留。

### 投影也要避开原生窗口栏

Electron 主窗 `titleBarOverlay.height = 40`，原生层盖在 Web 层之上，**y ∈ [0, 40] 的 DOM `elementFromPoint` 命中但真实点击到不了**。

侧栏与会话区顶边都是 y=0，所以早年「放在开头」的搬移必然从 y=0 起——实测会话头搬到侧栏后投影在 (0,0) 279×40，**40px 全部被盖住**，拖拽手柄与按钮在桌面端全部失效，Web 端看着完全正常。

现行做法：`relocateResolveFrame` 与 `projectionStep` 都把落点夹到 `projectionTopBound()`（40 = 窗口栏高度本身，**不留余量**）。

**下界不要留余量**：元素顶端在 y=40 已完全可点。早先写 44 会让「目标本来就在 40」的情况被硬推 4px，表现为 `dy: 4` 的假性不对齐——那个偏差是自己造的。

**不要复用 `launcherTopBound()`**：它取「页头底边 + 6」，是给恢复按钮用的（按钮不该压页头内容）。搬移的源本来就来自页顶，用这个下界会把它推到侧栏顶部内容上、制造新遮挡。两处下界语义不同，各自独立。

诊断脚本 `.tmp/probe-windowbar.js`：列出所有 fixed 层元素的坐标并标出落在窗口栏里的。

### 槽位化时期的两张表已删除（第十六轮）

`RELOCATE_SOURCE_SHAPES`（21 个单元的形状类别）与 `RELOCATE_SLOTS`（16 个槽位的 `minWidth` / `stack`）**已经删除**。

它们存在的唯一理由是：配置时不知道用户想放哪，只能从已知容器里选，于是必须回答「这个源能不能进那个容器」。画框之后这个问题不存在——用户画出什么位置就是什么位置，宽度是画的，高度是内容的。连带删除：`relocateSlotAccepts` / `relocateSlotsFor` / `RELOCATE_SHAPE_NEEDS` / `RELOCATE_MIN_WIDTH_RATIO` / `relocateFit` / 链式剔除。

当时的记录仍有效，作为**教训**保留：约束前置比运行时兜底好，但当「被约束的那个维度本身不需要存在」时，正确做法是把维度删掉，而不是把约束做得更准。

## 联动：规则是叠加层，不是新机制

规则（条件 → 动作）不引入新的运行时能力，只是给已有能力加一个「按条件生效」的开关：

- 条件读的是**当前识别结果**：页面判定沿用现成的优先级（设置页 > 会话页 > 插件详情页 > 外部插件页 > 插件页）；折叠看 `[data-dshl-frame][data-sidebar-collapsed]`；区域在场用 `areaLive`；单元在场看 target 表与 slots 渲染状态。
- 动作只有两种，都复用已有链路：隐藏生成 `display:none`（块 / 拆解单元 / 槽位条目各按自己的标记），容器排列生成网格规则。
- `computePlan(targets, config)` 把它们合成「基础配置 + 命中规则的叠加层」，样式与投影只认 plan。规则不命中就等于不存在，所以不会污染基础配置，也不会留下残余样式。
- 条件必须**每轮重算**：`refresh` 里除了重新识别，还会重算 plan 并重写动态样式与投影；否则切页面、折叠侧栏时规则不会即时生效。样式写入前比较文本，条件没变就不动 DOM。
- 命中状态直接显示在规则行上（命中 / 未命中），便于排查「为什么没生效」——多数情况是条件不成立而不是规则写错。

## 配置同步：两套 order 写在同一排图标上

面板导航卡按 `aria-label` 写 `[data-dshl-panel]` 的 order，插件来源卡按条目键写 `[data-dshl-slotentry]` 的 order；这两个属性落在同一排面板图标上，两套配置不一致时谁后写谁赢，用户会看到「在插件来源里上移了，但看起来顺序不对」。

同步的做法是**写配置时双向镜像**：从 DOM 里取两侧的一一对应（`sidebar.panellist` 条目 → 它渲染成的面板行，行上同时有 `data-dshl-slotentry` 与 `data-dshl-panel`），在任一侧排序/隐藏后，把另一侧的配置写成一致；开启状态下两套 order 数值恒等，冲突自然消失。反向写面板顺序时，不在同步范围内的面板保持原有相对次序、排在后面。

实测：开启同步后把 `media-desk` 上移，`slots.order` 写入 `-1`、`sidebar.panelOrder` 同时变成 `["自媒体工作台"]`；在面板导航里拖动，`panelOrder` 与 9 条 `slots.order` 一并写出；隐藏「演示文稿」后两侧隐藏配置同时出现、再开回来同时清除。

## 入口收纳：七区，三个原生 + 一个注入 + 三个授予式

侧栏入口越装越多时，把不常用的收进各区域内的「更多」菜单。三个区宿主自带原生「更多」（菜单行本来就由插件注册）：`sidebar.panellist.actions` / `conversation.session.header.views.actions` / `sidebar.right.tab.guide.actions`。会话头工具行没有 actions 槽位，但自带一个「更多操作」按钮——直接把收纳行注入它的菜单，按钮区不再多一个「更多」（见下节）。剩下三个区（设置页导航、插件页「已安装插件」分组、设置页页头操作）没有可用的「更多」，于是授予一个同款：

- **自动发现**：侧栏读 `sidebar.panellist` 槽位条目、会话视图读 `conversation.view` 条目（`chat` 不参与）、设置页导航读 `settings.section` 条目（约 22 项），右栏开始页读 DOM `[data-sidebar-right-guide-entry]`、插件页读 DOM `[data-plugin-package]` 卡片；会话头工具行与设置页页头操作扫容器里的 `button`（跳过「更多操作」——它是收纳入口本身）。新插件、新视图、新设置页、新按钮自动出现，无需登记。
- **身份键**：不按显示名认入口，按宿主自己的稳定键（详见「身份键：不靠显示名」）：视图与设置导航用列表 key（= 槽位条目 id），开始页用 kind，按钮用槽位条目键 / 列表 key / 业务组件名。
- **收起**：侧栏 `[data-dshl-panel] { display:none }`；视图标签、开始页卡片、设置页导航行、按钮由注解层按稳定身份匹配后打 `data-dshl-stored-*`；插件页直接按 `[data-plugin-package="<包名>"]` 收起。
- **打开**：三个原生区用 owner 的 `onOpen` / `layout.selectPanel`；会话头注入行与授予区都点原生控件本身——设置页导航点隐藏的导航行（React onClick 照常触发），插件页点卡片里的打开按钮，按钮类入口直接 `.click()` 被收起的原按钮（`display:none` 不影响 React 事件）。
- **授予式「更多」的做法**：在目标容器里插一个 `display:contents` 的外来锚点，锚点内的按钮运行时抄原生控件的 className 与内部结构（设置页抄非激活 navCell，插件页抄 extensions 组的 groupMore，页头操作抄原生按钮），菜单用宿主 `Menu` primitives。锚点由组件维护：容器出现/重建自动重挂（900ms 轮询兜底），卸载时移除；配置为空或 primitives 缺失时锚点不出现——宿主改版只会退化为不出现，不会破坏原界面。
- 宿主内部三套 Pin（面板、视图、开始页卡片）都只存在内存、刷新复位，也只经各自条目 inject 暴露，插件既读不到持久化也写不进去——所以不依赖，收纳状态写我们自己的配置。
- 边界：宿主保留的入口（侧栏「插件」、`chat`、开始页「文件」、会话头「更多操作」）不参与收纳，保证收起后永远有路可回；关闭「启用自定义布局」时菜单也不出收纳行。
- 实测：七区各收一个入口后都从原列表消失、各自「更多」菜单最前面列出并可点开（设置页切到模型页、插件页进入插件详情、会话头「更多操作」菜单里多出收纳行并可打开设计工作台/上下文诊断）；收纳状态刷新后保留。

## 更多操作：用宿主现成的「更多」

会话头工具行本来就有宿主「更多操作」按钮（复制会话 / 下载日志 / 反馈）。再插一个授予式「更多」会让同一行出现两个「更多」，所以改为注入它的菜单：

- **识别锚点**：按业务组件名 `SessionLogDownloadHeaderAction` 或槽位条目键后段 `session-log-download` 认按钮，不依赖文案；每轮注解给它打 `data-dshl-morehost`，宿主重建元素后自动补标记。
- **注入时机**：捕获阶段监听 `document` 的 click（只认 `data-dshl-morehost` 的按钮），记录当时已有的 `[role="menu"]` 集合，然后 40ms 轮询等「不在集合里的新菜单」出现——宿主菜单是异步打开的，且同一时刻可能有别的菜单（我们的授予式菜单）。
- **注入内容**：在 `[role="menu"]` 下的 `[role="presentation"]` 末尾追加一条分隔线 + 每个收纳项一行。行的 className 与内部结构从菜单里现有行**运行时读取**（宿主类名是哈希），图标用自绘 SVG（宿主用 `#dsw-icon-*` 的 use 引用，名字不对外保证）。
- **生命周期**：宿主每次打开菜单都重建 DOM，关闭时整棵移除——注入节点跟着消失。所以每次打开都重新注入，也不会重复叠加（`data-dshl-more-injected` 兜底）。
- **点击与关闭**：行点击 `.click()` 被收起的原按钮，再向 `document` 派发 `Escape`——宿主不知道菜单里多了一行，不会自己关。
- **回退**：宿主「更多操作」不在场时，会话头退回原来的授予式锚点；设置页页头操作没有原生「更多」，一直用授予式。
- **代价**：注入依赖宿主菜单结构；宿主大改版后注入会落空（收纳项仍在被收起状态但菜单里打不开，关掉配置即复原）。注入行不进宿主的键盘导航，方向键/Tab 不会停上来，鼠标可用。

## 身份键：不靠显示名

收纳状态要跨刷新记住「哪一个入口被收起」，配置里的键必须稳定。最初用显示名做键，宿主一改文案（本地化、产品改名、快捷键提示被拼进标题）就失配：已收起的入口找不到、点不开，面板里标成「此刻不在场」。改为按宿主稳定身份后，显示名只负责展示。

实测可用的身份来源（Web 客户端）：

| 入口 | 稳定身份 | 说明 |
| --- | --- | --- |
| 会话视图标签 | 按钮的 React fiber `key` = 视图条目 id（`trajectory` / `session-superagent-desk` …） | 宿主用 `key={view.id}` 渲染标签 |
| 设置页导航 | 导航按钮的 fiber `key` = 分区条目 id（`agents-md` / `models` …） | 同上 |
| 右栏开始页卡片 | `data-sidebar-right-guide-entry` 的值（kind） | 同一时刻唯一，不随标题与快捷键变化 |
| 按钮 | 槽位条目键（自身或祖先包裹层）→ fiber `key` → 最近业务组件名 | 设置页页头操作的槽位键打在包裹层上，所以向上找 3 层；无槽位键的按钮只剩组件名，如 `SessionLogDownloadHeaderAction` |

- 读取顺序固定：槽位键 → fiber key → 业务组件名 → 显示名；配置存第一个可用值（按钮存 `comp:<组件名>` 或完整槽位键，视图与设置导航存条目 id，开始页存 kind）。
- 匹配时任一身份命中即算同一入口；旧 `label:` 键继续按显示名匹配，早期只有名字的条目也回退显示名。
- 组件名不是稳定契约：宿主可能压缩或重命名组件，所以排在槽位键与列表 key 之后。同名组件（如 `HeaderButton`）不会被当成两个不同入口——实际命中靠槽位键。
- `files`（开始页「文件」）被排除在自动发现之外：宿主保留的兜底入口，收起后没有可用的「更多」能回到它。
- 会话头「更多操作」同样排除：它是会话头收纳的注入目标，收起后收纳项就没有地方放。

### 判空必须用 hasStorageId（第二十一轮修）

`normalizeConfig` 的 `storageZone` 会**把空 id 整个删掉**（`if (id !== '') record.id = id`），所以「没有稳定 id」的条目在运行期是**没有 id 字段**（`undefined`），不是空串。

运行期代码早先写 `entry.id !== ''` 判空——`undefined !== ''` 为真，于是：

| 位置 | 后果 |
| --- | --- |
| `findStoredFor` | 进入 id 分支后 `continue`，**label 兜底分支永远到不了** → 无 id 条目的收纳开关完全无效 |
| 按钮匹配 | 进入 `entry.id.startsWith(...)` → **TypeError** → 整个 `annotateStored` 中断，后面所有入口的收纳状态都不生效 |
| 视图菜单 | `filter((entry) => entry.id !== '')` 放行无 id 条目 → `undefined` 当 React key |

统一收口成 `hasStorageId(entry)`（判「非空字符串」）。这条与「身份键判空要判非空字符串」是同一类坑——那一处在 `storageKeyOf` 里早就修过，但这几处漏了。

**留一笔教训**：`undefined !== ''` 是 JS 里最容易写出来的假判空。凡是「某个字段可能被删掉」的归一化产物，判空都必须带类型检查。

## 槽位标记的时序

槽位条目的 `data-dshl-slotentry` 由本插件扫描后自己写上，不是宿主原生属性，于是有两个时序坑：

1. `refresh()` 原来先 `annotate(targets)` 后 `annotateSlotEntries()`，收纳匹配读到的是上一轮的旧标记。改为先打槽位标记、再识别与注解。
2. 槽位扫描有 1.5s 缓存（避免流式输出时反复遍历 React 树）。设置页这类「后打开的面板」第一次 refresh 可能还在缓存期内，拿不到标记。`scanSlotsIfStale()` 在「存在未渲染条目、且对应槽位出口已经出现在 DOM」时提前让缓存失效（限 300ms 一次），保证面板打开后的第一次或第二次 refresh 就能补上标记。

## 布局方案：为什么是整套快照

用户把布局调舒服了，往往要针对不同场景再调一套（写代码时窄侧栏 + 收起入口；演示时宽屏 + 放大字号）。写死的预设做不到这件事：预设是固定模板，用户自己的调法存不下来；而且预设只覆盖三栏与侧栏块，不碰收纳、联动这些后来的层。

选了最省事也最不容易出错的路：**方案就是一份完整配置**。

- 配置本来已经是单一事实源（`normalizeConfig` 校验、`localStorage` 持久化、`buildDynamicCss` 单一渲染入口），方案不需要新数据模型，只需要「多存几份」。
- 应用复用 `replaceConfig`：与「恢复默认」「导入 JSON」完全同一条链路。新增一套应用路径就要重复「校验 → 持久化 → 重算样式 → 通知」，两份实现必然漂移。
- 正因为是整套快照，**切换是覆盖而不是合并**。卡片描述里写死这句话：用户以为「切方案只改三栏」而发现收纳和规则也被换掉，是这类功能最容易踩的坑。
- `active` 只是「这套是我当前改动的起点」，不阻止继续手改（手改不清空它）——如果手改就清空，用户在方案上调完再点「覆盖」的路径会变得别扭。
- 上限 20 套、读取即截断：`localStorage` 里一份配置约 1.5 KB，20 套不足一个屏幕的图片大小；真正需要防的是界面被无限条目撑爆，所以在读取层截断并写回，而不是等用户触发写入。

**写回判据是个坑（第二十一轮修）**：写回条件曾经写成 `state.list.length > LAYOUTS_MAX`，但 `readLayouts()` 在读取阶段就已经 `break` 过，返回长度永远不超过上限——**那个条件恒假，写回是死代码**。存储里第 21..25 条于是既读不出来、也永远留在存储里，不清理也不提示。

现在由 `readLayouts()` 自己报告 `truncated`（只在真的因上限 `break` 时置位），`readLayoutsNormalized` 据此决定写回。三种情形都验过：

| 存储 | 读回 | 写回 |
| --- | --- | --- |
| 25 条 | 20 条 | 是（真截断） |
| 正好 20 条 | 20 条 | 否（没截断） |
| 含脏条目 | 丢弃脏条目 | 否（只是丢脏，不是截断） |

判据**不能**写成「raw 比规范化后的 state 长」——规范化本来就会丢弃非法条目，用它当条件会在任何一次「存储里有脏条目」时把整张表覆盖成残缺版本（历史上因此清空过方案表）。

## 持久化：为什么主存储搬到宿主侧

配置最初只存 `localStorage`。换浏览器、换个 Web 端口、清一次缓存，用户调了很久的布局就归零——这类损失比「配置不生效」更伤人，因为它无声无息。

- **为什么不自己写文件**：`ctx.get('fs')` 只有 Host 侧能用，且要宿主授权目录；客户端插件拿不到。自己管路径、并发、原子写，等于把宿主已经做好的事重做一遍。
- **为什么选 `configForms`**：它是宿主给 UI 插件的正规通道——Host 侧声明 schema，客户端读写字段，落盘与并发归宿主。`ui-theme`、`ui-locale`、`ui-conversation` 都走这条路。
- **字段为什么是 JSON 字符串**：配置字段随版本演进（storage / arrange / relocate / rules / sync / schemes 一路加过来）。若在 schema 里展开，每次加字段都要同步；而 schema 校验失败会让宿主**丢弃整节配置**——为了一条新字段的疏忽丢掉用户全部布局，代价太大。字符串 + 客户端 `normalizeConfig` 做权威校验更稳。
- **只 volatile 字段可写**：当前 `dsh-settings` 的 `write()` 会逐路径校验 `isVolatilePath`，没有 `.volatile()` 的字段直接抛错。这也是排查时的一个坑：schema 写对了、但漏 `.volatile()`，读得到、写不进。
- **落盘在 profile 的 `cordis.patch.yml`**：当前版本的设置就是 profile patch 的编辑面；`settings.yaml` 只留一次性导入。**排查这类问题必须解当前 `D:\DSH` 的 asar**——本机另有一份 `D:\deepseek-harness` 源码，是停滞的旧版本，照它推会得出错误路径。
- **双层存储的分工**：localStorage 负责「立即有界面」，宿主负责「永不丢」。启动先用缓存渲染，宿主读回后以宿主为准覆盖；宿主服务不在场则全程走缓存（降级，行为与改造前一致）。
- **回环防护**：写入串行化 + 记住最后写入值，读回到自己写的内容就跳过。否则「写 → 宿主回灌 → 再写」会转起来。
- **回环防护必须用「写入在途」判定，不能用字符串相等**（第十轮踩过的坑）：`hostForm.set` 是异步的，从发出到落地之间，宿主仍会推来它自己那份**旧快照**。而旧快照本来就与当前值不同——实测本地写入 5438 字节、宿主推回 5401 字节，少的正是刚加的那条收纳记录。任何「不相等才应用」的判据都会把它当成外部改动应用回去，表现为「点一次收纳生效，随即又被放出来」（30 次点击复现 3 次）。正确做法：`hostWrite` 时记一份 pending，写入 promise 落地后清掉；pending 非空期间收到的宿主快照整份跳过；再留 4 秒超时兜底，避免写失败后永远收不到外部改动。
- **配置改为显式保存**（第十五轮）：上面那条是**对抗**竞态，显式保存是**消除**竞态。`updateConfig` / `replaceConfig` 只改内存并标脏，不再落盘；`saveConfig()` 是唯一的持久化入口；`configIsDirty()` 为真时宿主快照整份跳过。宿主永远收不到中间态，回退与循环从根上消失。代价是未保存草稿只在内存里（刷新即丢），面板用常驻徽标提示。
- **一次性迁移**：宿主字段为空时把浏览器现值推上去。否则升级到宿主存储的第一天，用户只要不动任何设置，旧配置就永远留不在新存储里。

## 配置生命周期

- 首次启用时用当前界面的真实宽度做快照（`captureGeometry`），避免一开开关就跳变；同时把当前面板顺序写进配置，保证之后新增面板不会插到最前。
- 每次修改都经过 `normalizeConfig`：数值夹取、枚举清理、面板名去重；持久化防抖 250ms。
- 「恢复默认」= 换回默认配置（`enabled:false`）并清空动态样式；编辑浮层同时退出。

## 观察与性能

- `MutationObserver` 观察 `document.body` 的 `childList`（设置面板 portal 在 body 下，只观察 `#root` 会漏掉它），回调合并到 120ms 一次；只在识别结果变化（区域集合、面板名集合、设置面板有无）时才通知 React，流式对话的高频 DOM 变更不会引起无谓重渲染。
- 只观察 `childList`、不观察 `attributes`：注解器写自身属性不会触发回环。
- 编辑浮层自己用 `ResizeObserver` + `resize` 事件测量，不依赖注解回调的频率。

## 已知风险

- 宿主改版若去掉 `data-slot` 或改侧栏内部结构，块/面板识别会退化，编辑区提示「未识别界面结构」，覆盖样式为空。
- 与其它改外壳的插件同时启用时，谁后写 CSS 谁生效；本插件的 `!important` 更靠后，优先级更高。
- 面板以 `aria-label` 作为身份：切换界面语言后，旧配置里的面板名可能对不上，对应面板会回落到默认顺序。
